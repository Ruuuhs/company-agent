**作成日**: 2026-04-14
**作成者**: 戦略立案者（経営企画部）
**対象読者**: 代表
**ステータス**: ドラフト

## エグゼクティブサマリー

現状のリポジトリは「チームの骨格」として機能しているが、日々の対話で生まれる知識・判断・文脈がセッションをまたいで蓄積されない構造的欠陥がある。推奨は**選択肢A「文脈蓄積型・段階的進化」**：まず`context/`フォルダを新設して会社コンテキストの永続化から着手し、次にドキュメントの3層ライフサイクル管理を整備、最終的に自動腐敗検知まで進化させる。3段階・約6ヶ月で「毎日対話するたびにリポジトリが賢くなる」状態を実現できる。コストは代表の習慣変更が主で、追加ツール導入は最小限に抑える。

---

## 1. 現状の課題（3つ以内）

### 課題1：会社コンテキストが「空白のテンプレート」のまま

`guidelines/company-overview.md` は `（your company name）`などのプレースホルダーが残っており、AIが毎セッションで「この会社は何をしているか」をゼロから推測する状態になっている。エージェントが本来の力を発揮できない根本原因。

### 課題2：日次の対話ログ・意思決定履歴が消えている

毎日の経営判断・却下した施策・承認した方針が、セッション終了とともに消滅している。「先週なぜこの方針にしたか」をAIも代表も参照できない。リポジトリが育っていない最大の理由。

### 課題3：ドキュメントに「有効期限」の概念がない

`outputs/` 内に生成されたドキュメントが増えるほど、古い情報と新しい情報の区別がつかなくなる。現状の保存期間ルール（output-standards.md）は「保管するか捨てるか」の2択で、「更新が必要か」の腐敗検知設計がない。

## 2. ドキュメント種別と寿命の設計

### 3層モデルの概念

```
Layer 1（一時）: tmp/         → 30日で自動削除対象
Layer 2（中期）: outputs/     → 1〜7年保管（種別によって異なる）
Layer 3（永続）: guidelines/  → 恒久的に維持・更新
                context/      → 新設。会社の「記憶」として永続管理
```

### 各層の詳細定義

| 層 | フォルダ | 寿命 | 役割 | 更新頻度 |
|----|---------|------|------|---------|
| 一時 | `outputs/tmp/` | 30日 | 作業中ドラフト・検討中メモ | セッション単位 |
| 中期 | `outputs/reports/` `outputs/documents/` | 1〜7年 | 確定したレポート・成果物 | 月次〜年次 |
| 永続 | `guidelines/` | 無期限 | ルール・スタンダード | 随時（判断の都度） |
| 永続 | `context/`（新設） | 無期限 | 会社の記憶・意思決定ログ | 日次 |

### 昇格フロー

```
[一時層] セッション中のメモ・試案
    ↓ （判断：再利用価値があるか？）
[中期層] 確定したアウトプット（reports/等に保存）
    ↓ （判断：今後も判断基準として使うか？）
[永続層] guidelines/ または context/ に昇格・統合
```

#### 昇格基準

| 条件 | 一時→中期 | 中期→永続 |
|------|---------|---------|
| 代表が承認した | ✓ 必須 | — |
| 3回以上参照された | — | ✓ 推奨 |
| 経営判断の根拠になった | ✓ 推奨 | ✓ 必須 |
| 類似ケースの雛形になる | — | ✓ 必須 |
| 方針・ルールが変わった | → 上書き or アーカイブ | → guidelines更新 |

### 各新設ファイルの役割詳細

#### `context/company-state.md`（最重要）
AIが毎セッション冒頭に読み込む「現在の会社の状態」。以下を含む：
- 直近30日の主要KPI（数値）
- 現在進行中の最優先プロジェクト（3つまで）
- 直近の重要な意思決定（最新3件）
- 今月のフォーカステーマ

#### `context/decisions-log.md`
経営判断の永続ログ。形式：
```
## YYYY-MM-DD｜[判断の概要]
- 判断内容:
- 判断理由（根拠）:
- 却下した選択肢:
- 次回見直し予定:
```

#### `context/rejected-ideas.md`
却下した施策のログ。「なぜ却下したか」を残すことで、同じ議論の繰り返しを防ぐ。

#### `guidelines/maintenance-schedule.md`
定期メンテナンスの手順書（後述のセクション6と連動）。

## 4. 進化の3段階オプション

### 選択肢A（推奨）：文脈蓄積型・段階的進化

**コンセプト**: 「今日から始められる最小コスト」で会社コンテキストの永続化を実現し、段階的に自動化・高度化していく。

- **Phase 1（今すぐ）**: `context/` フォルダ新設 + `company-overview.md` の実情報入力
- **Phase 2（1〜2ヶ月）**: 日次ログ習慣の確立 + 週次メンテナンス導入
- **Phase 3（3〜6ヶ月）**: 腐敗検知の仕組み化 + テンプレート拡充

**メリット**:
- 代表の追加負担が最小（1セッションで15分以内）
- 既存構造を壊さずに追加するだけ
- 効果が1週間以内に体感できる

**リスク**:
- `context/` の更新を怠ると「古い記憶」になる（→ 日次ルーティンで対処）
- 実行難易度: **低**

---

### 選択肢B：完全自動化型

**コンセプト**: GitHooksやCronジョブを導入し、ドキュメント管理を自動化する。

- 毎日自動でメンテナンスチェックリストを生成
- `tmp/` の自動削除スクリプト
- KPIを外部データソースから自動取得してcontext更新

**メリット**:
- 代表の手動作業が最小化される
- スケールしやすい

**リスク**:
- 初期セットアップに技術的工数が必要
- スクリプトのメンテナンス負担が発生する
- 自動化への依存でブラックボックス化するリスク
- 実行難易度: **高**

---

### 選択肢C：保守的アプローチ（現状維持＋最小改善）

**コンセプト**: 現在の構造を維持しつつ、`company-overview.md` の充実だけに集中する。

- `company-overview.md` を詳細に記入
- 週次で手動レビューのリマインダーを設定

**メリット**:
- リスクがほぼゼロ
- 実行難易度: **最低**

**リスク**:
- 意思決定ログが残らない（課題2が未解決）
- 1〜2ヶ月後に「やっぱり足りない」となる可能性が高い
- 実行難易度: **最低**

---

### 比較表

| 評価軸 | 選択肢A（推奨） | 選択肢B | 選択肢C |
|--------|--------------|--------|--------|
| 期待効果 | 高（文脈の永続化＋意思決定蓄積） | 最高（自動化） | 低（最小改善） |
| リスク | 低（習慣継続リスクのみ） | 中（技術的複雑性） | 中（根本課題が残る） |
| 実行難易度 | 低 | 高 | 最低 |
| 初期コスト | 2〜3時間 | 1〜2日 | 30分 |
| 効果発現 | 1週間以内 | 1ヶ月後 | 即日（但し限定的） |
| 拡張性 | 高 | 最高 | 低 |

## 6. 定期メンテナンスフロー

### 日次アクション（所要時間：5〜10分）

```
【セッション開始時】
□ context/company-state.md を読んで前回の続きから始める
□ context/ongoing-projects.md で進捗を確認

【セッション終了時】
□ 今日の重要な意思決定を context/decisions-log.md に記録（3行以内）
□ ongoing-projects.md の状態を更新（進捗・ブロッカー）
□ company-state.md の「今月のフォーカス」が変わっていれば更新
```

### 週次アクション（所要時間：15〜30分、推奨：毎週月曜）

```
□ context/weekly-summary.md を更新（先週の活動・判断・学び）
□ outputs/tmp/ を確認し、中期層に昇格するファイルを仕分け
□ ongoing-projects.md の期日切れ・遅延プロジェクトをレビュー
□ rejected-ideas.md に先週却下したアイデアを追記
□ company-state.md の主要KPIを最新数値に更新
```

### 月次アクション（所要時間：60〜90分、推奨：月初の第1営業日）

```
□ 月次振り返りレポート（templates/月次振り返り.md）を作成・保存
□ decisions-log.md を読み返し、パターン・傾向を分析
□ 中期層（outputs/）に蓄積されたドキュメントのうち、永続層への昇格候補を選定
□ guidelines/ の各ファイルを読み、実態と乖離していないか確認
□ 全エージェント定義を一通りレビュー（役割変更が必要なものをメモ）
□ tmp/ フォルダのクリーンアップ（30日以上経過したファイルを削除）
□ 翌月のフォーカステーマを company-state.md に記入
```

## 7. リスクと対応策

| リスク | 発生確率 | 影響度 | 対応策 |
|-------|---------|-------|--------|
| 日次ログを更新する習慣が定着しない | 高 | 高 | セッション終了コマンドを定型化する（「終了」と言うと自動でdecisions-log更新のプロンプトが出るように設計） |
| `context/` の情報が古くなり「嘘の記憶」になる | 中 | 高 | company-state.mdに「最終更新日」フィールドを必須化。週次チェックリストで確認 |
| ドキュメントが増えすぎてAIのコンテキストを圧迫する | 中 | 中 | 各ファイルに文字数上限を設定（company-state.mdは1,000字以内など） |
| guidelinesと実態の乖離（ルールが形骸化） | 中 | 中 | 月次レビュー時に必ず一読し、乖離があれば即日更新する |
| 重要ドキュメントの誤削除 | 低 | 高 | git管理されているため復元可能。tmpフォルダ以外は手動削除を避ける |
| エージェントの役割が実務と合わなくなる | 中 | 低 | 月次レビューで見直し。違和感を感じたらその都度メモをrejected-ideas.mdに記録 |

- **仮説・未検証事項**:
  - 日次ログ習慣が定着するまでの期間は個人差がある。2週間試してみて、負担感が高い場合は週次のみに頻度を落とすことを検討。（要検証）
  - 選択肢B（自動化）の実現可能性は、代表のGit/スクリプト運用スキルによって変動する。現時点では選択肢Aを推奨するが、Phase 2以降で再評価を推奨。（仮説）
