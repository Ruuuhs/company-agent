# 収益設計書: LLM Observability受託スタートアップ サービス設計・収益モデル

**作成日**: 2026-04-24
**作成者**: 収益設計者（事業開発部）
**対象**: LLM Observability受託スタートアップ（新規立ち上げ）
**ステータス**: ドラフト

---

## エグゼクティブサマリー

国内でLLM Observability専門受託はcloudpack（KDDIアイレット）がほぼ唯一の競合であり、オンプレ対応・ツール非依存という軸で明確な差別化ニッチが存在する。本設計では、**7サービスメニューの段階的展開**と**3年間の収益シミュレーション**を提示する。

推奨収益構造は「初期構築フィー（一括）＋月次ランニング（継続）」の二層モデルである。3年目の標準シナリオで年間売上2.4億円・営業利益率32%を目標とし、ユニットエコノミクスはLTV/CAC比25倍で成立する。参入ウィンドウは2026〜2027年と限定的なため、1年目は案件実績の蓄積とブランド確立に集中することを推奨する。

**重要**: 本書の数値はすべて仮定に基づく試算である。実際の価格設定・原価確認は財務コントローラーとの連携、契約スキームの設計は法務チェッカーの確認が必要である。

## 2. 課題・改善機会

### 立ち上げ期の本質的課題

1. **実績ゼロの信頼性問題**: 受託ビジネスは「誰がやってくれるのか」が発注の決め手。技術ブログ・OSS貢献・登壇での信頼構築が収益化の前提条件となる。
2. **案件単価の幅が広い**: 50万円のアセスメントから800万円のオンプレ構築まで幅広く、案件ミックスが収益の安定性を左右する。高単価案件（オンプレ構築・ランニング契約）へのパイプラインをどう作るかが鍵。
3. **エンジニア調達コストと粗利のバランス**: LLMOps + インフラ + Observabilityを横断できる人材は希少。正社員採用のみでは固定費が重く、フリーランス・業務委託の比率設計が重要。

## 3. サービスメニュー設計

### サービスA（推奨・入口）: LLM Obs現状アセスメント

**内容**: 既存LLMシステムの可観測性診断。トレーシング・コスト管理・品質評価の現状ギャップ分析とツール選定ロードマップ提供。成果物: アセスメントレポート（20〜30ページ）+ 推奨アーキテクチャ図。

**ターゲット**: 本番運用に移行済みまたは移行検討中の中堅企業・スタートアップ。IT/SaaS・製造・金融系。従業員300〜3,000名規模。

**提供期間・工数**: 2〜3週間・エンジニア1名 × 10〜15人日

**価格設定**:
- 価格: 75万〜120万円/件（中央値95万円）
- 根拠（価値ベース）: AI開発コンサル相場（月40〜200万円）の0.5〜0.7ヶ月分。「現状が分からないと何も始まらない」という顧客の初期ニーズに応える入口商品として、意思決定しやすい単価帯に設定。

**必要スキル・人員**: LLMOpsエンジニア1名（Langfuse/OTel経験者）、PM兼営業0.3名

**粗利率の見込み**: 65〜70%
- （仮定）直接原価: エンジニア15人日 × 6万円/日 = 90万円の工数コスト → 中央値95万円での粗利率は5万円/95万円 = 5%（人月単価を下げる or 工数を効率化することが必要）
- 修正前提: エンジニアが効率化テンプレートを活用し実質10人日で完了した場合、原価60万円 → 粗利率37%（仮定）
- 中長期的にはアセスメントの型化・テンプレート整備で粗利率65%以上を目指す

**戦略上の位置づけ**: ランニング契約・構築案件へのエントリーポイント。アセスメント顧客の50%（仮定）が後続のサービスB/Cに移行することを前提としたフロントエンド商品。

### サービスB（主力）: OSSスタック型Observability環境構築

**内容**: Langfuse OSS + ClickHouse + OpenTelemetry + Grafanaによるセルフホスト型LLM観測環境の設計・構築・初期設定。クラウド（AWS/GCP/Azure）またはオンプレに対応。プロンプトトレース・コスト可視化・品質評価パイプラインを含む。

**ターゲット**: データ主権への配慮からDatadog SaaS等の外部サービスを採用できない中堅・大手企業。金融・製造・情報通信業。従業員500名以上。

**提供期間・工数**: 4〜8週間・エンジニア2名 × 30〜50人日（規模による）

**価格設定**:
- 小規模（クラウド構築、OSSのみ）: 180万〜250万円
- 標準（クラウド + カスタムダッシュボード + 評価パイプライン）: 280万〜400万円
- 大規模（オンプレ + マルチ環境 + ガードレール実装）: 450万〜700万円
- 根拠（コスト積み上げ + 価値ベース）: エンジニア2名 × 40人日 × 6万円/日 = 480万円の工数コスト（固定費含む）に対し、競合のcloudpack（Datadog依存型）より20〜30%低い価格でOSSベースの構築を提供。顧客にとってはDatadogライセンス費（月数十万円〜）を節約できるため、ROIが明確に説明できる。

**必要スキル・人員**: LLMOpsエンジニア2名（Langfuse + ClickHouse + Kubernetes経験者）、PM1名

**粗利率の見込み**: 標準案件（300万円想定）で
- （仮定）直接原価: エンジニア2名 × 35人日 × 6万円/日 = 420万円
- 上記では赤字のため、前提を修正
- （仮定・修正前提）エンジニア単価を業務委託フリーランス想定（日率4.5万円）で計算すると原価315万円 → 粗利率 = (300万-315万) = △ → 標準案件単価350万円が採算ライン
- **採算確保のための最低価格: 350万円（エンジニア2名×35人日、フリーランス活用時）**
- 採算ライン確保後の追加マージン分（間接費・PM工数を含む）まで考えると推奨単価は400万円以上

> **財務コントローラーへの確認依頼**: エンジニア原価（社員・業務委託別）の正確な単価を基にした採算ラインの再計算を依頼する。本書の数値は仮定であり、確定前に必ず確認が必要。

### サービスC（継続収益の核）: 月次Observability運用代行

**内容**: 構築済みLLM観測環境の継続監視・月次レポート・アラート対応・コスト最適化提案。毎月: 品質スコアレポート / コスト推移分析 / 異常検知アラート対応 / 改善提案1件以上。

**ターゲット**: サービスB完了後の既存顧客。または他社構築済み環境の引き継ぎ。

**提供期間・工数**: 月次継続（最低6ヶ月契約）・月8〜15人日

**価格設定**:
- ライト（月次レポート + アラート対応のみ）: 月30万〜40万円
- スタンダード（レポート + アラート + コスト最適化提案）: 月50万〜70万円
- プレミアム（上記 + 週次ミーティング + 改善実装1〜2件含む）: 月80万〜120万円
- 根拠: LLMOコンサル相場（月50万円〜）に準拠。「監視」だけでなく「改善提案」を含む価値ベース設計。

**必要スキル・人員**: エンジニア0.5名（担当顧客複数社を掛け持ち可能）

**粗利率の見込み**: 70〜75%
- （仮定）スタンダード60万円/月: エンジニア12人日 × 4万円/日（一人あたりの間接費込み）= 原価48万円 → 粗利20%
- テンプレート化・自動化が進むほど粗利率は改善。1エンジニアが5社担当できれば粗利率65〜70%（仮定）

**LTV計算**:
- スタンダード60万円/月 × 平均24ヶ月継続 = 1,440万円（ランニングのみ）
- 初期構築（サービスB）350万円 + ランニング1,440万円 = **LTV 1,790万円/顧客（仮定）**

### サービスD（高単価）: オンプレLLM専門Observability構築

**内容**: vLLM / Ollama等のオンプレLLM実行環境に対する専門的なObservabilityスタック構築。外部SaaS不可の金融機関・官公庁・製造業向け。Prometheus + Grafana + Langfuse セルフホスト + OpenTelemetry Collector の完全内製構成。

**ターゲット**: 金融機関・官公庁・防衛・医療機関。プロンプト・ログデータが外部ネットワークに出せない組織。従業員1,000名以上。

**提供期間・工数**: 2〜5ヶ月・エンジニア2〜3名 × 60〜120人日

**価格設定**:
- 標準オンプレ構築: 500万〜700万円
- 大規模マルチ環境（複数部署・複数LLM）: 700万〜1,200万円
- 根拠（価値ベース）: インフラ構築案件相場（200〜800万円）の上位帯。競合が対応できない領域であり、代替手段がない顧客に対してプレミアム価格が正当化される。Datadogライセンス不要のため、顧客の年間コスト削減が数百万円規模になるROI提示が可能。

**必要スキル・人員**: SRE/インフラエンジニア1名 + LLMOpsエンジニア1〜2名 + PM1名

**粗利率の見込み**: 40〜55%
- 工数が大きく、専門性の高い人材が必要なため粗利率は他サービスより低め
- （仮定）標準600万円案件: エンジニア3名 × 80人日 × 5万円/日 = 原価1,200万円 → 赤字
- 修正前提: 単価見直しが必要。エンジニア2名 × 60人日 × 5万円/日 = 原価600万円 → 販管費考慮前で粗利率0%
- **採算確保: エンジニア2名 × 60人日で工数コスト600万円なら、最低700万円〜の受注が必要**
- 長期ランニング契約（月60万〜）とのセット受注を前提とした価格設定が現実的

### サービスE（差別化）: 業種特化ガードレール設計・実装

**内容**: 金融（景表法・金融商品取引法対応）、製造（設計情報漏洩防止）、医療（禁忌情報誤出力防止）など業種固有の要件に対応したガードレール実装。NeMo Guardrails / LlamaFirewall / 独自ルールエンジンを活用。

**ターゲット**: 規制業種（金融・医療・法務・教育）でLLMを本番導入済みの企業。コンプライアンス部門が関与する大手企業。

**提供期間・工数**: 3〜6週間・エンジニア1〜2名 × 20〜40人日

**価格設定**:
- 基本ガードレール実装（1業種・3〜5ルール）: 200万〜300万円
- フルカスタマイズ（法的要件分析から実装まで）: 350万〜600万円
- 根拠（価値ベース）: コンプライアンス違反リスクを「防止」できることへの対価。金融機関にとって1件の情報漏洩は数億円規模の損害 / 制裁リスクがあり、数百万円の予防投資は正当化される。

**必要スキル・人員**: LLMエンジニア1名（NeMo Guardrails経験） + 対象業種のドメイン知識（外部専門家との連携も可）

**粗利率の見込み**: 55〜65%（テンプレート化が進むほど改善）

**価格設定**:

- 月次サポート: 月20万〜40万円

**必要スキル・人員**: MLエンジニア1名（RAGAS/DeepEval経験者）

**粗利率の見込み**: 60〜70%（評価フレームワークのテンプレート化が進めば高粗利）

## 5. ユニットエコノミクス

### LTV計算

**標準顧客ジャーニー（サービスA → B → C）**:
- A（アセスメント）: 95万円（仮定）
- B（OSS構築）: 350万円（仮定）
- C（運用代行）: 60万円/月 × 24ヶ月 = 1,440万円（仮定）
- **LTV合計: 1,885万円/顧客（仮定）**

**ランニングのみ継続顧客（オンプレ構築後）**:
- D（オンプレ構築）: 700万円（仮定）
- 月次ランニング: 80万円/月 × 36ヶ月 = 2,880万円（仮定）
- **LTV合計: 3,580万円/顧客（仮定）**

### CAC計算

**顧客獲得コスト（仮定）**:
- 技術ブログ・登壇・OSS貢献（インバウンド）主体の場合:
  - マーケ費（外注デザイン・イベント参加費）: 月20万〜30万円（仮定）
  - エンジニアの技術発信にかかる間接時間: 月10人日 × 6万円/日 = 月60万円（仮定）
  - 合計マーケコスト: 月80〜90万円（仮定）
  - 1年目の月次受注件数: 0.5〜1件/月（仮定）
  - **CAC = 月90万円 / 0.75件 = 120万円/件（仮定）**
- 紹介・クラウドベンダーパートナー経由の場合:
  - 紹介フィー5〜10% + 営業費: CAC60〜80万円（仮定）

**LTV/CAC比**:
- 標準顧客ジャーニー: 1,885万円 / 120万円 = **約15.7倍（仮定）**
- オンプレ高単価顧客: 3,580万円 / 120万円 = **約29.8倍（仮定）**
- いずれも「LTV > CAC × 3」の基本ラインを大幅に超過。ユニットエコノミクスは成立する（仮定前提）。

## 7. 価格戦略

### 値付けのロジック

**基本姿勢: 価値ベース価格設定を優先し、コストベースを下限として使用する**

| 価格設定手法 | 適用タイミング | 具体的な使い方 |
|------------|-------------|-------------|
| 価値ベース | 主要サービス（B・D・E） | 「Datadogライセンス年間300万円の削減」「情報漏洩リスク回避の価値」を定量化して価格を正当化 |
| 競合比較 | アセスメント・構築系 | cloudpack（Datadog依存型）より10〜20%低価格かつOSS活用でランニングコスト優位性を訴求 |
| コスト積み上げ | 価格交渉時の下限設定 | 工数原価 × 1.4〜1.6倍を最低価格として交渉上の防衛ラインとする |
| 心理的価格 | 月次ランニング | 50万円・80万円・120万円の3段階プランで選択肢を作り、中央帯（80万円）に誘導する |

### 競合との価格ポジショニング

```
高価格
│   大手SIer（NTTデータ等）: 月100万〜/専任チーム
│   Accenture: エンタープライズ専用
│
│   cloudpack: DatadogライセンスSaaS込みで月60万〜100万円
│
│ ← 自社ポジション: OSSベース・オンプレ対応・月30万〜80万円
│   ツール非依存・中堅〜大手向け
│
│   フリーランスエンジニア: 単発対応、月30万〜50万円
低価格
```

自社は「大手より安く・フリーランスより信頼できる・特定ツールに依存しない」ポジションを目指す。

### 段階的な価格アップの設計

| フェーズ | 期間 | 価格方針 | 理由 |
|---------|------|---------|------|
| 立ち上げ期 | 1〜4ヶ月 | 市場相場の80%価格 | 初期実績・事例作りを優先 |
| 実績構築期 | 5〜12ヶ月 | 市場相場の95% | 2〜3社の成功事例でほぼ正規化 |
| ブランド確立期 | 2年目 | 市場相場の100〜110% | 「オンプレ×LLM Obs」専門家ブランドで正規化 |
| プレミアム期 | 3年目以降 | 市場相場の110〜130% | 業種特化・独自ノウハウで価格プレミアムを正当化 |

**立ち上げ期の値引きルール**:
- 値引きは最大20%まで（それ以上は採算割れリスク大）
- 値引きの代替として「期間短縮」「スコープ縮小」を優先して提案
- 初期顧客には「参照事例として公開許諾をいただく条件で割引」という交換条件を活用する

### リピート率向上の仕組み

1. **サービスの階段設計**: アセスメント → 構築 → ランニングという「次のステップ」を初回提案時から見せる
2. **成果の数値化**: 月次レポートで「前月比コスト削減率〇%・品質スコア〇点」を可視化し、継続の理由を定期的に提供する
3. **担当者の関係性**: 担当エンジニアをクライアントの社内LLMチームに「仮想メンバー」として参加させる（週次の技術Slackに参加等）
4. **アップセルのタイミング設計**: ランニング3ヶ月目に「次フェーズ提案（ガードレール追加・評価パイプライン構築）」を定例化
5. **年次レビュー商談**: 年1回の契約更新を「年次LLM Obsレビューミーティング」として設定し、価格改定・スコープ追加を合わせて提案

## 8. 外部連携・パートナーシップ戦略

### スキーム1: AWSパートナーネットワーク（APN）活用

**連携相手**: Amazon Web Services（APN Advanced / Select Tierパートナー）

**スキームの概要**:
APNパートナーに登録し、AWS Marketplaceへのリスティング、AWSの顧客向けソリューションアーキテクト（SA）からのリファーラルを受け取る体制を構築する。

**自社のメリット**:
- AWSのSAからの案件紹介（インバウンドリード）
- AWSロゴ・パートナーバッジによる信頼性向上
- AWS Activateなどのスタートアップ向け支援プログラム（AWS Creditsなど）
- AWSのイベント（re:Invent Japan、AWS Summit）での登壇機会

**相手方のメリット**:
- AWSクラウド上でのLLM Observability構築案件がAWSのEC2/ECS/EKS等のクラウド消費増加に直結する
- 顧客が「AWSを使ってLLM Obsを構築できた」という成功事例をAWSが活用できる

**Win-Winの根拠**: 自社の構築案件がAWSインフラ消費を直接増やすため、AWSはコスト不要で自社を紹介することに合理性がある。

**収益分配の条件**: 紹介フィーなし（リファーラルベース）。コンサルティングパートナーとしての関係のみ。Marketplace掲載の場合はAWSへの手数料3〜20%が発生（要確認）。

**リスクと対応**:
- リスク: AWSがLLM Obs専門サービスを自社開発した場合（Amazon Bedrock等の機能拡充）
- 対応: クラウド非依存・オンプレ対応という差別化軸を維持し、AWS専属化を避ける

**法務確認ステータス**: 未依頼（APNパートナー契約締結前に法務チェッカーへ確認依頼が必要）

### スキーム2: Langfuseコミュニティ + OSSコントリビューション

**連携相手**: Langfuse OSS（ClickHouseが2025〜2026年に買収）、OpenTelemetry GenAI SIG

**スキームの概要**:
Langfuseのセルフホスト実装に関する日本語ドキュメント・ブログ・サンプルコードをOSSとして公開する。OpenTelemetry GenAI SIGへのフィードバック参加。

**自社のメリット**:
- 「Langfuse日本語専門家」としてのブランド確立 → インバウンドリード獲得
- OSSコントリビューターとしての採用ブランディング（エンジニア採用に有効）
- グローバルコミュニティへのアクセスによる最新情報の早期取得

**相手方のメリット**:
- LangfuseにとってJapanese市場での採用拡大・日本語ドキュメントの充実
- OpenTelemetryにとって日本企業での実装事例の蓄積

**Win-Winの根拠**: OSSコミュニティは「使う人・広める人」を常に必要としており、日本語圏での普及者として自社が価値を持てる。

**収益分配の条件**: 金銭的な取引なし。情報・ブランド・紹介機会の相互提供。

**リスクと対応**:
- リスク: ClickHouseによるLangfuse買収後に製品の方向性が変わる（有償化・機能制限等）
- 対応: 特定OSSへの過度な依存を避け、OpenTelemetry標準への準拠を中核に置く

**法務確認ステータス**: 不要（OSSコミュニティへの参加は契約不要）

### スキーム3: 中堅SIer・ITコンサルとのサブコン連携

**連携相手**: 中堅SIer（地場SIer・専門SIer）、コンサルファーム（AI導入支援を行うが、Observability実装が手薄なプレイヤー）

**スキームの概要**:
AI導入支援プロジェクトを受注した中堅SIerが、「LLM Observabilityの実装」部分を自社（スタートアップ）に外注（サブコントラクト）する。または、大手コンサルのサブコンとしてインフラ実装を担当する。

**自社のメリット**:
- 大企業顧客への間接アクセス（通常ではリーチできないセグメント）
- 案件の安定供給（繁忙期のキャパシティ確保）
- SIer顧客の既存関係を活用した信頼性補完

**相手方のメリット**:
- LLM Observabilityという専門性の不足を補える
- 顧客への提供サービスの幅を拡大できる
- 自社リソース不足時の案件リスクを分散できる

**Win-Winの根拠**: SIerは「何でもできる」を顧客に見せたいが、LLM Obsの専門人材は社内に少ない。専門家として信頼できるサブコンの存在は、SIerの提案競争力を高める。

**収益分配の条件**:
- サブコン形態: 自社がSIerから工数単価（月70〜100万円/エンジニア）で受注
- マージン: SIerが20〜30%マークアップして顧客請求
- 注意: 過度なサブコン依存は自社の顧客直接接点を失うリスクがある。直販比率を70%以上に維持することを目標とする。

**リスクと対応**:
- リスク: SIerが自社ノウハウを習得した後に内製化・関係を打ち切る可能性
- 対応: 最新技術のアップデート・独自ノウハウの継続的積み上げで代替されにくい関係を維持する

**法務確認ステータス**: 未依頼（業務委託契約・NDA締結前に法務チェッカーへの確認依頼が必要）

## 10. 推奨案と実施計画

**推奨**: OSS構築（サービスB）とランニング（サービスC）をコアに、アセスメント（サービスA）を入口とした三層モデル

**推奨理由**:
1. **LTVが最大化できる**: アセスメント → 構築 → ランニングのジャーニーで1顧客LTV1,500万円以上を実現できる
2. **技術ブログとの相性が良い**: OSSスタック（Langfuse + OTel）はまさに「エンジニアが書くべき技術コンテンツ」であり、顧客獲得と技術ブランド構築が同時に進む
3. **競合が対応できない領域に集中できる**: オンプレ対応・ツール非依存はcloudpack（Datadog依存型）との明確な差別化になる

**実施ステップ**:
