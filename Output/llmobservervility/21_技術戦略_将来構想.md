## 第9章：技術戦略

### 9-1. 技術戦略の根幹思想

当社の技術戦略は「Observabilityは商品ではなく、腕前の証明である」という一文に集約される。

LLM品質保証サービスを受託で提供するとき、Observabilityの仕組みそのものを売るのではない。「あなたのシステムが本番でどれだけ正しく動いているか」を数字で示せる能力——つまり腕前——を顧客に売る。

この思想から導かれる技術選択の原則は3つある。

**原則1: OSSファースト**
自社が特定のベンダーに依存した瞬間、顧客に「中立性」を提供できなくなる。Langfuse、OpenTelemetry、RAGAS、DeepEvalはいずれもオープンソースであり、顧客環境のオンプレ・プライベートクラウドにそのまま持ち込める。

**原則2: 標準準拠**
OpenTelemetry GenAIセマンティック規約という業界標準に乗ることで、将来のツール入れ替えに強い構成を顧客に提供できる。独自プロトコルは短期的に便利でも、長期では技術負債になる。

**原則3: 評価エンジンの自社開発**
トレーシングとデータ基盤はOSSで調達できる。しかし「日本語LLMの出力が正しいかどうかを判定する評価エンジン」は市場に存在しない。ここだけは自社で開発し、他社が真似できない知的資産にする。

### 9-2. 採用技術スタック（2026年最適解）

#### スタック全体像

```
[計装・収集層]
  アプリケーションコード
    └── OpenTelemetry Python SDK
         + openllmetry（LLMフレームワーク対応の計装ライブラリ）
         + opentelemetry-instrumentation-openai
         ↓
  OpenTelemetry Collector（集約・変換・フィルタリング）

[トレーシング・可視化層]
  Langfuse v3（MIT License）
    + PostgreSQL（メタデータ・プロジェクト設定）
    + ClickHouse（大量トレースの高速分析）
    + Redis/Valkey（キャッシュ・キュー）
    + MinIO/S3（大容量ペイロード保存）

[評価層]
  LLM-as-a-Judge（Claude 3 Opus / GPT-4o をジャッジとして使用）
    + RAGAS（RAGパイプライン評価）
    + DeepEval（エージェント・マルチターン評価）
    + 自社開発：日本語評価エンジン（後述）

[ガードレール層]
  NeMo Guardrails v0.20（Apache 2.0）
    + LlamaFirewall（Meta OSS、2025年4月リリース）

[可視化・アラート層]
  Grafana（ダッシュボード）
    + Prometheus（メトリクス収集）

[インフラ]
  Docker Compose（開発・中小規模）
  Kubernetes（大規模・エンタープライズ）
```

#### 各コンポーネントの選択根拠

**トレーシング: OpenTelemetry + Langfuse OSS**

OpenTelemetryのGenAI SIGは2024年4月に発足し、LLM呼び出し・エージェントステップ・ベクトルDB検索のセマンティック規約を策定中である（2026年4月時点で大半がExperimentalステータス、2026年内にStable移行見込み）。DatadogがOTel v1.37から本番サポートを開始しており、業界標準としての地位は事実上固まっている。

Langfuseは2026年1月にClickHouseに買収され（ClickHouseは$400M Series Dで調達）、MITライセンスが維持されたまま開発が加速している。GitHub Stars 21,000以上・SDKインストール月2,600万件・Fortune 500の63社が採用。ClickHouseとの統合が深化したことで、自社スタックの中核として据える根拠が一層強固になった。

Langfuse v3のアーキテクチャはトレースをS3に書き込み → Workerが ClickHouseに投入するパイプラインを採用しており、大量トレースでも高速分析が可能な設計になっている。

**評価: LLM-as-a-Judge + RAGAS + DeepEval**

LLM-as-a-Judgeは人間評価との一致率約80%を達成しつつ、コストを500〜5,000倍削減できる。2026年時点のベストプラクティスとして、Chain-of-Thought推論の要求・位置バイアス対策（(A,B)と(B,A)の両順序で評価）・Cohen's Kappaによる一貫性検証が確立されている。

RAGASはRAGパイプライン特化で4指標（Faithfulness / Answer Relevance / Context Precision / Context Recall）を提供。DeepEvalはエージェント・マルチターン会話・MCP tool useへの対応が進んでおり、2026年時点ではRAGASの次のステップとして使うのが定石。MLflowもDeepEval・RAGASのサードパーティジャッジ統合を2026年に追加しており、エンタープライズ案件での採用障壁が下がっている。

**ガードレール: NeMo Guardrails / LlamaFirewall**

NeMo Guardrails v0.20（2026年1月リリース）は5種類のレール（入力・ダイアログ・取得・実行・出力）を持ち、OTelトレーシング対応・GPU並列実行で1.4倍の検知率向上を実現。Thoughtworks Technology Radar 2026でAdoptステータスに移行しており、エンタープライズ展開の実績が積み上がっている。

LlamaFirewall（Meta、2025年4月リリース）はPromptGuard 2（プロンプトインジェクション検知）・AlignmentCheck（エージェント逸脱検知）・CodeShield（コード安全性）の3モジュールで構成され、Meta本番環境で運用実績がある。LlamaFirewallはシンプルなブロッキングに優れ、NeMo Guardrailsは細粒度のダイアログ制御に優れる。両者を層状に組み合わせる構成が2026年の実践的な選択肢になっている。

**データ基盤: ClickHouse + PostgreSQL**

LangfuseのアーキテクチャがClickHouse + PostgreSQLを標準採用しており、自社スタックとの整合性が完璧である。ClickHouseは高速列指向クエリにより、数百万件のトレースを数秒で集計できる。PostgreSQLはプロジェクト設定・ユーザー管理・プロンプトバージョン等のトランザクションデータを担当する。

**可視化: Grafana**

vLLM + Prometheus + GrafanaによるセルフホストLLM推論監視は2026年時点で実用的な技術として確立されている。GrafanaはDatadogの約1/10のコストで同等の可視化を実現でき、オンプレ顧客への提案において最大の武器となる。

### 9-3. OSSファースト戦略の合理性

OSSファーストを選ぶ理由は4つある。

**理由1: コスト競争力**
DatadogのLLM Observabilityは月間1億トークンで数百万円規模になりうる。OSSスタックのインフラコストは同規模で月5〜20万円程度に収まる。顧客のコスト問題を解決することが自社の価値になる。

**理由2: データ主権の確保**
日本の金融機関・官公庁・医療機関の多くは、プロンプト（患者情報・機密情報・顧客情報を含む）を外部SaaSに送れない。OSSセルフホストは唯一の解決策であり、この領域のグローバルSaaSは対応できない。

**理由3: カスタマイズの自由度**
業種特化のガードレールルール・日本語評価ルーブリック・FISC準拠のログ構造——これらはSaaSでは設定変更の範囲内に収まらない。OSSのコードレベルでの改修・拡張ができることが、専門受託事業者としての本質的な価値になる。

**理由4: ベンダーロックインからの自由**
Langfuseに障害が起きてもOpenTelemetry準拠のスタックであれば他のバックエンドに切り替えられる。OpenTelemetryという共通基盤の上に実装することで、特定ベンダーの商業判断に事業の命運を握られない。

OSSの持続可能性リスクについて補足すると、Langfuse（ClickHouseに買収・MITライセンス維持）、OpenTelemetry（CNCF傘下のガバナンス）、Grafana（上場企業によるOSS運営）はいずれも2026年時点で事業継続性が確認できるプロジェクトである。RAGAS・DeepEvalは商用版が存在し、OSSのサポートが続く構造になっている。

### 9-4. OpenTelemetry GenAI準拠の重要性

OpenTelemetry GenAI SIGは2024年4月に発足し、以下の属性を定義している。

| 属性 | 意味 |
|------|------|
| `gen_ai.operation.name` | 操作種別（chat / embeddings / completions） |
| `gen_ai.system` | モデルプロバイダー（openai / anthropic / aws.bedrock） |
| `gen_ai.request.model` | 使用モデル名 |
| `gen_ai.usage.input_tokens` / `gen_ai.usage.output_tokens` | トークン数 |
| `gen_ai.agent.name` | エージェント名 |
| `invoke_agent` / `create_agent` | エージェント呼び出しスパン |

これに準拠することの実利は「ベンダー乗り換えコストがゼロに近くなる」点にある。現在Langfuseを使っていても、OTel準拠で実装していれば将来Arize PhoenixでもGrafana Tempoでも切り替えられる。

顧客にとっては「特定のObservabilityツールのロックインを回避できる」という価値になる。これは受託事業者として最も誠実な提案である。競合のDatadog依存型サービスと対比したとき、最も強い差別化軸の一つになる。

2026年内にStable仕様への移行が見込まれており、今のうちにExperimentalで実装しておくことが先行者優位につながる。仕様変更のキャッチアップを受託の技術的価値として顧客に提示できる。

出典: [OpenTelemetry GenAI セマンティック規約](https://opentelemetry.io/docs/specs/semconv/gen-ai/)（継続更新・公式）
出典: [AI Agent Observability - OTel公式ブログ](https://opentelemetry.io/blog/2025/ai-agent-observability/)（2025年）

### 9-5. 日本語評価エンジンの開発方針

#### なぜ自社開発が必要か

英語向けのLLM評価フレームワーク（RAGAS・DeepEval・Braintrust）を日本語に適用しようとすると、以下の問題が発生する。

- 敬語・丁寧語の一貫性を測定できない（英語に敬語の概念がない）
- 日本語の曖昧表現（「〜かもしれません」「〜ではないでしょうか」等）を意味解釈できない
- 和製英語・業界固有の日本語語彙を正しく扱えない
- 景品表示法・薬機法・金融商品取引法等の日本固有の法規制に照らした出力チェックができない
- デジタル庁「源内」で採用された国産LLM（tsuzumi 2、PLaMo 2.0 Prime、cotomi v3等）の評価基準が整備されていない

グローバルプレイヤーは日本語評価エンジンを作る動機を持たない。これが最大の参入障壁であり、自社が守れるポジションである。

#### 開発方針

**フェーズ1（0〜6ヶ月）: 基盤評価ルーブリックの設計**

まず対象ドメイン（社内ナレッジ検索・文書要約・FAQ対応等）ごとの日本語評価軸を言語化する。評価軸の例として以下を想定している。

| 評価軸 | 意味 | スコア方式 |
|--------|------|---------|
| 文体一貫性 | 敬語・丁寧語の混在がないか | 0/1 Pass-Fail |
| 事実整合性（日本語文脈） | 回答が提供情報と矛盾しないか | 0〜1 スコア |
| 法規制準拠 | 景表法・薬機法等の禁止表現が含まれないか | 0/1 Pass-Fail |
| 日本語自然度 | ネイティブが読んで違和感がないか | 1〜5 スコア |
| 曖昧表現の適切性 | 不確実な内容に対して適切にhedgingされているか | 0/1 Pass-Fail |

**フェーズ2（6〜12ヶ月）: LLM-as-Judgeとして実装**

設計した評価ルーブリックを、Claude / GPT-4oへのシステムプロンプトとして実装する。Chain-of-Thought推論を要求し、「なぜそのスコアを付けたか」の根拠も記録する。評価スコアのCalibration（人間のレーターとのKappa係数測定）を定期的に実施する。

**フェーズ3（12〜18ヶ月）: 業種別テンプレートとしてライブラリ化**

初期の受託案件から蓄積された評価データをもとに、業種別評価テンプレートをライブラリ化する（詳細は第10章に後述）。

デジタル庁の「ガバメントAI（源内）」が2026年3月に国産LLM7モデルを選定し、評価基準として「ハルシネーション・バイアス・有害コンテンツ・説明可能性」を設定している。この政府基準を参照しつつ、民間向けの実用的な評価テンプレートを先行して整備することで、政府・民間両方の顧客に対応できる評価基盤を作る。

出典: [デジタル庁 ガバメントAI源内 LLM選定結果](https://www.digital.go.jp/assets/contents/node/information/field_ref_resources/10d55c63-b3e1-42b9-9cc5-93a06943ae0e/51df3410/20260306_policies_ai_govai_result_of_the_open_recruitment_process.pdf)（2026-03-06）

### 9-6. エージェントトレーシングの実装戦略

#### なぜエージェントトレーシングが最重要課題か

マルチエージェント・ツール呼び出しを伴うAIシステムでは、1件のユーザーリクエストが「10〜20回のLLM呼び出し + 複数のツール実行 + メモリ読み書き」に展開される。従来のAPMツールはこれを追跡できない。

2026年2月時点のインシデント原因分布（Datadog State of AI Engineering調査）:
- レート制限超過: LLMスパンエラーの60%
- コンテキスト切れ（トークン上限超過）
- ツール呼び出し失敗
- 無限ループ・暴走エージェント

これらは標準的なサーバー監視では検知できない。エージェントを本番運用している組織の94%が何らかのObservabilityを実装しており、フレームワーク採用率は2025年初頭の9%超から2026年初頭に18%超へ倍増している。

#### 実装の3層構成

**第1層: スパン設計（エージェントの動き全体を追跡）**

OpenTelemetryのGenAI規約における`invoke_agent`・`create_agent`スパンを使い、エージェントの各ステップを親子関係でつなぐ。これにより「どのサブエージェントが・どのツールを・どの順序で呼び出したか」が時系列で可視化できる。

```
[UserRequest] ─ root span
  ├── [OrchestratorAgent] ─ invoke_agent
  │     ├── [LLM Call 1] ─ gen_ai.operation.name: "chat"
  │     ├── [ToolCall: web_search] ─ tool span
  │     └── [LLM Call 2] ─ gen_ai.operation.name: "chat"
  ├── [SubAgent A] ─ invoke_agent
  │     └── [LLM Call 3]
  └── [SubAgent B] ─ invoke_agent
        └── [LLM Call 4]
```

**第2層: 評価スコアの紐付け（品質を数字で残す）**

各スパンに評価スコアを添付する。Langfuse v3の`score`機能を使えば、トレースIDに対して後から評価スコアをバッチで投入できる。本番稼働中のトレースを一定割合でサンプリングし、LLM-as-Judgeで評価し、スコアをフィードバックするパイプラインを構築する。

**第3層: アラートと異常検知（問題を即座に発見する）**

Grafanaのアラートルールで以下を常時監視する。
- エラー率が直近1時間で5%を超えたらSlack通知
- 平均レイテンシが直近30分でP99 > 10秒になったらアラート
- コスト（入力/出力トークン数 × 単価）が日次予算の80%を超えたら警告

この3層を受託案件の標準実装として確立し、「エージェントが何をしているかを完全に追跡できる状態」を納品物の定義とする。

## 第10章：将来構想 — ISMAP/FISC対応のLLM品質管理SaaSへの進化

### 10-1. 受託からプロダクトへの移行シナリオ

#### なぜプロダクト化を目指すのか

受託事業は「人が動く限り売上が上がる」モデルである。これは最初の実績を積む段階では正しい戦略だが、スケールに上限がある。

プロダクト（SaaS）は「一度作れば何社にも売れる」モデルである。LLM品質管理SaaSへの移行を目指す理由は3つある。

1. 受託で蓄積した知見（評価テンプレート・ベンチマークデータ・FISC準拠ログ構造）はプロダクトに転換できる知的資産である
2. ISMAP/FISC対応という参入障壁の高い領域でのSaaSは、グローバルプレイヤーが短期間で追いつけない
3. 規制対応SaaSは顧客の乗り換えコストが高く、チャーンが起きにくい

#### 受託→プロダクトの段階的移行

```
[Year 1〜2: 受託専業]
  受託案件の実行 → 知見の蓄積
  日本語評価ルーブリックの設計・検証
  業種別ガードレールのテンプレート作成
  FISC準拠ログ構造の確立
         ↓
[Year 2〜3: ハイブリッド]
  受託を続けながら、蓄積した知見をSaaSのプロトタイプに変換
  初期ユーザー（既存受託顧客）にベータ版として提供
  フィードバックを受けてプロダクトのPMFを検証
         ↓
[Year 3〜5: プロダクト主体]
  ISMAP-LIU登録の取得（低リスク業務向けSaaSとして政府調達の対象に）
  月額サブスクリプション型の本格展開
  受託はカスタマイズ要件の大型案件のみに絞り込む
```

移行の判断基準として、以下のいずれかを達成した段階でプロダクト化への本格投資を決定する。

- 同一の評価テンプレートを3社以上の顧客に提供し、いずれも有効と評価された
- 受託納品物のうち70%以上が共通コンポーネントで構成されている
- 月次顧問契約が5社を超え、評価・監視の継続サービス需要が確認できた

### 10-2. ISMAP/FISC対応SaaSとして設計する理由

#### 規制対応は最大の参入障壁になる

ISMAP（政府情報システムのためのセキュリティ評価制度）とFISC安全対策基準（第13版、2025年3月改訂・AI安全対策基準を新設）は、日本固有の規制要件であり、グローバルSaaSが日本市場で後回しにしがちな対応領域である。

現在のISMAP登録LLM関連サービスの状況（2026年4月時点）:
- GaiXer（FIXER社、ISMAP-LIU登録 2024年12月）: Azure OpenAI Service基盤
- AWS Amazon Bedrock（ISMAP登録済み）: プラットフォームのみ、LLM品質管理サービスは非登録
- Langfuse Cloud（未登録）: セルフホスト版は顧客環境に依存するためISMAPの対象外

LLM品質管理に特化したSaaSとしてISMAP-LIUを取得すれば、政府・自治体・ISMAP準拠が要件の大企業調達において唯一の選択肢になる。

#### FISC第13版が新設したAI安全対策基準と自社SaaSの対応関係

| FISCのAI安全対策カテゴリ | 自社SaaSが提供する機能 |
|------------------------|---------------------|
| AIの適切な利用・運用管理 | プロンプト/レスポンスの品質スコア継続監視・ダッシュボード |
| AIに係る安全対策 | 異常検知・ガードレール・インシデント記録 |
| 方針策定・態勢整備 | 利用実績レポートの自動生成・経営層向けダッシュボード |
| 外部委託先管理 | LLMベンダー（OpenAI等）のAPIコスト・エラー率・SLA可視化 |

金融庁AIディスカッションペーパー第1.1版（2026年3月公表）が示すモデルリスク管理要件——LLM推論プロセスの記録・サードパーティ依存リスクの可視化・PII制御のログ記録——はすべて自社SaaSの機能設計に直接反映できる。

出典: [FISC第13版公表](https://www.fisc.or.jp/topics/006665.php)（FISC、2025年3月）
出典: [金融庁AIディスカッションペーパー第1.1版](https://www.fsa.go.jp/news/r7/sonota/20260303/aidp.html)（金融庁、2026-03-03）

### 10-3. 品質ベンチマークデータの資産化

#### データそのものが競合優位になる

受託案件を重ねるたびに、以下のデータが蓄積される。

- 業種別・用途別のLLM評価スコア分布（「金融文書要約タスクでのFaithfulnessスコアは平均0.82」等）
- 日本語LLMと英語LLMの品質差の定量データ
- ガードレールの誤検知率・見逃し率のベンチマーク
- モデル更新（サイレントアップデート）によるスコア変動パターン

これらは5〜10社のデータが集まった時点で「業界ベンチマーク」として機能し始める。「あなたの会社のFaithfulnessスコア0.72は、金融業界の中央値0.80を下回っています」という比較データが提供できるようになる。

#### データの資産化パイプライン

```
受託案件のトレース
    ↓
匿名化処理（顧客・プロンプト内容の削除）
    ↓
スキーマ標準化（業種・用途・モデル名・評価軸・スコア）
    ↓
ClickHouseのベンチマークDBに蓄積
    ↓
四半期ごとに業界別ベンチマークレポートとして公開（一部無償・詳細有償）
    ↓
ベンチマークレポートが新規顧客へのインバウンドを生む
```

ベンチマークデータは以下の3つの用途で資産として機能する。

1. **営業ツール**: 「競合他社と比較して自社LLMの品質はどうか」を知りたい顧客への提案資料になる
2. **製品差別化**: SaaSの「業界比較機能」として組み込み、他社が作れない機能になる
3. **思想的権威**: 「LLM品質のベンチマーク」を持つ会社として業界での発言力が上がる

### 10-4. 業界別評価テンプレートのライブラリ化

#### なぜライブラリ化するのか

評価テンプレートを個別の受託案件ごとに一から作るのは非効率である。テンプレートをライブラリとして整備・公開することで以下を実現する。

1. 受託の納品品質が均一になり、デリバリーコストが下がる
2. OSSとして公開することでコミュニティが育ち、採用ブランドになる
3. プロダクト化したときの「デフォルト評価テンプレート」として組み込める

#### ライブラリの設計

**第1フェーズ: 優先3業種のテンプレート整備（0〜12ヶ月）**

| 業種 | 評価テンプレートの骨格 |
|------|---------------------|
| 金融 | 景表法・金融商品取引法準拠チェック / 個人情報マスキング検証 / 投資助言の適切性評価 / 数値の正確性スコア |
| 製造 | 設備・工程用語の専門用語一致率 / 安全基準表現の適切性 / 英語・日本語混在文書の整合性 |
| 医療 | 禁忌・投薬情報の誤り検知 / 医療用語の正確性 / 患者情報マスキング検証 / 説明同意文書の明瞭性 |

**第2フェーズ: 官公庁・教育業種への拡張（12〜24ヶ月）**

デジタル庁のガバメントAI「源内」評価基準（ハルシネーション・バイアス・有害コンテンツ・説明可能性）を参照し、政府機関向けの評価テンプレートを設計する。2027年4月から政府調達が有償化される見込みであり、その前に評価基準を整備することで政府案件への提案力を高める。

**テンプレートの技術仕様**

各テンプレートは以下の構造で定義する。

```yaml
template:
  name: "金融機関向けLLM評価テンプレート v1.0"
  version: "1.0.0"
  industry: "financial"
  metrics:
    - name: "regulatory_compliance"
      type: "pass_fail"
      judge_model: "claude-opus-4"
      rubric: |
        以下の出力が景品表示法・金融商品取引法に違反していないか評価してください。
        違反している場合は0、問題ない場合は1を返してください。
      chain_of_thought: true
    - name: "numerical_accuracy"
      type: "score_0_1"
      judge_model: "claude-opus-4"
      rubric: |
        出力中の数値（金額・利率・期間等）が参照情報と一致しているか評価してください。
        完全一致: 1.0 / 軽微な差異: 0.5 / 重大な差異または欠損: 0.0
  calibration:
    human_agreement_target: 0.80
    kappa_target: 0.70
```

このYAML定義をDeepEvalまたはRAGASに渡すと、自動的に評価パイプラインが構築される設計にする。

### 10-5. 3〜5年後のビジョン

#### 2028〜2030年に到達したい状態

**「日本のLLM品質基準を作る会社」**

当社が目指すのは、ツールを売る会社でも、コンサルを売る会社でもない。「日本のLLM品質の標準を定義する会社」になることである。

具体的には以下の状態を2028〜2030年に実現する。

**1. ISMAP-LIU登録SaaSとしての政府調達実績**

ISMAP-LIU登録を取得し、政府・自治体のLLM品質管理SaaSとして調達実績を持つ。デジタル庁の「源内」エコシステムと連携し、国産LLMの品質評価インフラとしての地位を確立する。

目標時期: 2028年
必要条件: ISO/IEC 27001取得（2027年目標）→ ISMAP-LIU申請（2027〜2028年）

**2. 業界別ベンチマーク「JLM-Bench（Japan LLM Quality Benchmark）」の確立**

金融・製造・医療・官公庁の4業種において、日本語LLMの品質ベンチマークを定期公表する「JLM-Bench」を確立する。Nejumi Leaderboard（日本語LLMランキング）がモデルの性能を測るのに対し、JLM-Benchは「本番ユースケースでの品質」を測ることに特化する。

このベンチマークを権威あるものにするため、業界団体・学術機関との共同研究を積極的に推進する。

**3. 月間100社以上のSaaS顧客基盤**

受託からプロダクト主体に移行し、月額サブスクリプション型で100社以上の顧客基盤を持つ。受託はカスタマイズ案件のみに特化し、エンジニアの稼働効率を最大化する。

ARR目標: 5億円以上（Year 5）

**4. グローバル展開の検討**

日本語評価エンジンで培った「特定言語・文化圏に特化したLLM品質管理」という方法論は、韓国語・繁体字中国語市場にも応用できる。2028年以降のオプションとして韓国・台湾市場への展開を検討する。

当社の将来構想には複数のシナリオが存在する。経営判断の参考として、楽観・中立・悲観の3シナリオを整理する。

### 10-7. プロダクト化に向けた技術的準備事項

受託からプロダクトへの移行を実現するために、以下の技術的準備を段階的に進める。

**マルチテナント対応**

現在の受託実装は「1顧客 = 1環境」で設計されている。SaaS化にあたっては、複数顧客のデータを厳密に分離しつつ、単一のインフラ上で運用するマルチテナントアーキテクチャへの移行が必要になる。ClickHouseの行レベルセキュリティ機能とLangfuseのプロジェクト分離機能を組み合わせることで実現できる。

**APIファースト設計**

顧客のCI/CDパイプライン・既存のデータ基盤・社内ポータルからAPI経由で評価データを取得できるように、REST APIを標準インターフェースとして設計する。これにより「うちの環境に組み込める」という顧客の要望に応えられる。

**セキュリティ認証の取得**

SaaSとして顧客に提供する場合、当社自身のセキュリティ態勢を証明する必要がある。具体的には以下のステップで進める。

1. ISO/IEC 27001の取得（2027年目標）: 情報セキュリティ管理システムの認証
2. ISMAP-LIUの申請（2027〜2028年目標）: 政府調達の対象になるための登録
3. SOC 2 Type IIの検討（2028〜）: グローバル顧客対応のため

FISC安全対策基準の受託事業者としての要件（処理データの取り扱いポリシー・国内保管・監査対応体制）は、受託段階から整備しておくことでSaaS化時の認証取得コストを大幅に削減できる。

## 技術戦略・将来構想 まとめ

**第9章（技術戦略）の要点**

1. OSSファーストで顧客のデータ主権とコスト効率を同時に満たす
2. OpenTelemetry GenAI準拠でベンダーロックインなしの構成を提供する
3. 日本語評価エンジンの自社開発が唯一グローバルに真似できない競合優位になる
4. エージェントトレーシングの3層実装（スパン設計・評価スコア紐付け・アラート）を受託の標準納品物にする
5. 18ヶ月のロードマップは「技術検証 → 初期案件 → 技術資産確立 → プロダクト基盤」の4段階で進める

**第10章（将来構想）の要点**

1. 受託からプロダクトへの移行は3年かけて段階的に行う。急がない
2. ISMAP-LIU取得が政府・金融市場への最大の参入障壁になる。2027〜2028年を目標に取得準備を開始する
3. 品質ベンチマークデータは受託案件の副産物として蓄積され、3年後に「JLM-Bench」として権威を持つ
4. 業界別評価テンプレートのライブラリ化が受託品質の均一化とプロダクトの差別化を同時に実現する
5. 3〜5年後のビジョンは「日本のLLM品質基準を作る会社」。ツールでも人月でもなく、知的権威を売る
