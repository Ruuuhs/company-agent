# 顧客の実課題分析：なぜLLM Observabilityが必要か

**作成日**: 2026-04-24
**目的**: 本番LLMシステムで企業が直面している具体的・リアルな課題を整理し、事業提案の根拠および顧客ヒアリング・営業の素材とする
**情報源**: 複数技術ブログ・Datadog/LangChain公式ドキュメント・市場調査資料・OWASP・cloudpack事例

---

## サマリー：6つのリアルな課題

| # | 課題の名前 | 「困っていること」を一言で |
|---|-----------|----------------------|
| 1 | **ハルシネーション問題** | 「動いているのに間違える」がシステムの外から見えない |
| 2 | **コスト爆発問題** | APIトークン費用が月次で急膨張しているが誰も把握していない |
| 3 | **エージェント暴走問題** | 1回の質問が裏で20回AIに問い合わせていて、なぜ遅いか分からない |
| 4 | **オンプレ監視の空白問題** | データを外に出せないから、クラウド型の監視ツールが一切使えない |
| 5 | **規制ログ問題** | 「ログを取れ」と規制に書いてあるが、全部取るとプライバシーに引っかかる |
| 6 | **品質劣化に気づけない問題** | プロンプトを少し変えたら回答が悪化したが、数週間後に顧客クレームで初めて発覚 |

## 課題 1：ハルシネーション問題

### 何が起きているか

LLMは「エラーコードを返さずに間違った回答をする」という、従来のソフトウェアにはない特性を持つ。

Datadog公式ドキュメント（2025年）での指摘：
> 「従来のAPMは検索に400ms、LLM呼び出しに1.2秒かかったことを示せる。しかし示せないのは、**検索が誤った製品の文書を返したこと、LLMがコンテキストにない詳細をハルシネーションしたこと**、エンジニアが無関係なコードを修正したときにシステムプロンプトがドリフトしたことだ。」

LangChain（2025年）:
> 「レスポンスは高速で、ブランドトーンに合っていて、それでも間違っている可能性がある——**ハルシネーション、安全でない内容、または誤った文脈に忠実である場合がある**。これが、LLM Observabilityが評価機能をインフラダッシュボードと組み合わせる理由だ。」

### 具体的なシナリオ

```
状況：金融機関の社内FAQシステムにLLMを導入
実際に起きたこと：
  ユーザー「退職金の税計算はどうなりますか？」
  LLM回答：「退職所得控除は勤続年数×40万円です」（← 旧制度の数字）
  実際：2024年の税制改正で計算式が変更されていた
  システムログ：「200 OK, レイテンシ 0.8秒」← 正常応答として記録
  発覚のきっかけ：顧客の税申告後にクレームが来た
```

### なぜ従来ツールで検知できないか

| ツール種別 | 検知できること | 検知できないこと |
|-----------|-------------|---------------|
| Datadog（APM）| レスポンスタイム、エラー率 | **回答が古い税制の数字かどうか** |
| CloudWatch | APIコール数、レイテンシ | **ハルシネーションが発生しているか** |
| アプリケーションログ | 入出力のraw text | **その回答が正確かどうかの判定** |

### LLM Observabilityでの解決

- **LLM-as-Judge**：別のLLMが回答の正確性を自動評価（人間評価との一致率約80%）
- **セマンティックドリフト検出**：時系列での回答傾向変化をモニタリング
- **Faithfulnessスコア**：RAGシステムでソース文書と回答の整合性を定量化

## 課題 2：コスト爆発問題

### 何が起きているか

**数字で見る深刻さ**：
- LLM APIへの企業支出：2024年後半 **35億ドル** → 2025年中頃 **84億ドル**（約2.4倍）（出典：業界調査、2026年）
- cloudpack自社事例：LLM Observability導入前後で「年間 **31.2人日** の運用工数が削減」
- 2026年調査：**85%の組織** が「トークン追跡・コスト帰属が最優先のObservabilityニーズ」と回答

### 具体的なシナリオ

```
状況：EC企業が商品説明自動生成AIを本番稼働
実際に起きたこと：
  月初予算：月額API費 50万円を見込んでいた
  月末請求：API費 230万円の請求書が来た（4.6倍）
  原因を調査：
    → 商品登録フォームにバグがあり、同じ商品を1件登録するたびに
      GPT-4oが100回呼び出されていた（1回=100円 × 100回 = 1万円/商品）
    → 発見まで3週間かかった
  コスト：3週間 × 日300件 × 1万円/件 = 約630万円の過剰請求
```

### 見えていない問題

| コスト要因 | 把握できているか | Observabilityなしの問題 |
|-----------|----------------|----------------------|
| モデル別APIコスト | × | GPT-4とGPT-4oの使い分けが適切か分からない |
| ユーザー別消費量 | × | 誰のリクエストがコストを食っているか分からない |
| 機能別消費量 | × | どのAI機能が費用対効果が悪いか分からない |
| トークン最適化余地 | × | プロンプトを短くすれば20%節約できるか試算できない |

### LLM Observabilityでの解決

- **モデル別・ユーザー別・機能別コスト帰属（アトリビューション）**
- **トークン消費量のリアルタイムアラート**（月予算の80%到達でSlack通知）
- **コスト最適化提案**：どのプロンプトを短縮すれば何円節約できるかを可視化

## 課題 3：エージェント暴走問題

### 何が起きているか

AIエージェント（複数の機能を自律的に組み合わせるAI）を本番運用すると、「1回のユーザー入力が裏で10〜20回のAI呼び出しに展開される」という複雑さが生まれる。

**インシデント原因の実態**（エージェント本番運用組織の調査、2026年2月）：
- レート制限超過：エラーの **60%**
- コンテキスト切れ（トークン上限超過）
- ツール呼び出し失敗
- **無限ループ・暴走エージェント**

### 具体的なシナリオ

```
状況：旅行代理店の自動見積AIエージェント
設計：「フライト検索」→「ホテル検索」→「保険検索」→「見積書作成」の4ステップ

実際に起きたこと：
  ユーザーが「来月ハワイに行きたい」と入力
  正常時：4ステップ、約5秒で見積書完成
  異常時：
    → フライト検索ツールがタイムアウト
    → エージェントが「もう一度試みる」を自動的に繰り返す
    → 3時間後：同じAPIを2,400回呼び出し、費用2万円消費
    → ユーザーはずっと「処理中...」を見ていた
  発覚：課金明細が来て初めて判明

従来ツールで見えたこと：「APIエラー率が上昇」← 原因が分からない
Observabilityで見えること：
  「エージェント Step2（フライト検索）が47分前からリトライ中。
   現在243回目。コスト累計 ¥12,240。このまま続けますか？」
```

### なぜ急増しているか

- AIエージェントを採用している組織：2025年初頭 **9%** → 2026年初頭 **18%**（2倍）
- エージェントを本番運用している組織の **94%** が何らかのObservabilityを実装（必要性の高さの証拠）
- エージェントステップごとのトレースを取得している組織：**71.5%**

## 課題 4：オンプレ監視の空白問題

### 何が起きているか

金融機関・官公庁・大手製造業は「機密データを外部クラウドに送れない」制約から、LLMをオンプレ・プライベートクラウドに構築している。しかし：

**構造的な問題**：
- DatadogのLLM Observability → **SaaS前提。外部にデータを送信する設計**
- New Relic、Splunk等も同様 → **全てクラウドSaaS。オンプレでは使えない**
- オンプレLLMは「監視の空白地帯」に取り残されている

### オンプレLLMの実態

| ツール | 用途 | 普及度 |
|--------|------|--------|
| **vLLM** | 本番向け高性能推論エンジン。金融・製造業に増加 | 高 |
| **Ollama** | 開発・検証向けシンプル実行環境 | 高 |
| **llama.cpp** | CPU推論対応。エッジ・低リソース向け | 中 |
| **TGI（Hugging Face）** | PrometheusメトリクスをネイティブにPush | 中 |

**vLLMとOllamaには「システムメトリクス（レイテンシ・スループット）」の出力機能はある。しかし「プロンプト品質・ハルシネーション検出」はアプリ層での別途実装が必要。**

### 具体的なシナリオ

```
状況：地方銀行がオンプレで社内LLMを構築
制約：個人情報・融資情報があり、外部SaaaSへのデータ送信は金融庁が懸念を示している
試みたこと：
  → Datadog LLM Observability → 「SaaS。データ外部送信あり」→ 法務が拒否
  → New Relic LLM Monitoring   → 同上
  → 自社でPrometheus + Grafana  → LLMのシステム負荷は見えるが品質は見えない
  → Langfuse（SaaS版）           → 同上。外部送信問題あり
現状：
  → 何も監視できていない
  → ハルシネーションが発生してもAラートが来ない
  → FISC第13版のログ要件を満たせていない
```

### Observabilityでの解決（オンプレ専門）

```
解決構成（自社が提供できる唯一の構成）：
  vLLM / Ollama（オンプレ推論）
    ↓
  OpenTelemetry Collector（自社ネットワーク内）
    ↓
  Langfuse OSS（セルフホスト）+ ClickHouse（セルフホスト）
    ↓
  Grafana（可視化）

→ 外部にデータが出ない
→ FISC・ISMAPのログ要件を満たせる
→ ハルシネーション検出・コスト管理が可能
```

## 課題 5：規制ログ問題

### 何が起きているか

規制は「ログを取れ」と言っている。しかし全部のログを取ると別の問題が発生する。

**規制の要求**：

| 規制 | 要求内容 |
|------|---------|
| **デジタル庁 DS-920** | 「有害情報の出力制御」「ログ保存」「ハルシネーション対策」が政府調達の前提条件 |
| **FISC安全対策基準 第13版** | AI安全対策の4カテゴリ（方針策定・運用管理・**安全対策・監視**・教育）を要求 |
| **ISMAP管理基準** | ログ取得・保護・レビュー（A.12.4）が現行基準で要求。2027年改訂でAI固有要件が追加予定 |

**トレードオフ問題**：

```
全ログを取ると：
  → プロンプトに含まれる個人情報（氏名・住所・病歴）が保存される
  → 個人情報保護法：「取得したPIIは目的外利用禁止」
  → GDPR（欧州企業との取引がある場合）：「削除権」への対応が複雑になる

ログを取らないと：
  → DS-920の政府調達要件を満たせない
  → FISC第13版のAI監視要件を満たせない
  → 「なぜその回答をしたか」の説明責任が果たせない
```

### LLM Observabilityでの解決

- **PIIフィルタリング**：プロンプトからPIIを自動マスキングした上でログ保存（規制対応とプライバシーの両立）
- **サンプリング戦略**：全件保存ではなく「エラーが発生した呼び出しのみフルログ」等の設計
- **監査証跡の設計**：「いつ・誰が・何を入力して・何が出力されたか」を改ざん不可な形で保存

## 課題 6：品質劣化に気づけない問題

### 何が起きているか

LLMシステムの「静かな劣化」：プロンプトや外部ツールの変更後に品質が下がっても、誰も気づかない。

**実態（技術調査より）**：
- RAGシステム：チャンキング設定の変更が検索品質に**埋め込みモデルの選択と同等以上の影響**を与える
- プロンプトドリフト：「エンジニアが無関係なコードを修正したときにシステムプロンプトがドリフトした」（Datadog公式）
- 新規RAGデプロイの **60%** が「初日から体系的な評価を導入」（2025年初頭は30%未満）

### 具体的なシナリオ

```
状況：SaaS企業のカスタマーサポートAIチャットボット
タイムライン：
  2/1：エンジニアAがシステムプロンプトに3行追加（別バグ修正のついでに）
  2/1〜2/15：ユーザーからの「役に立たない」評価が増加（15% → 32%）
  2/15：サポートリーダーが「なんか最近AIの回答おかしくない？」と報告
  2/17：エンジニアが原因調査開始
  2/22：「2/1のシステムプロンプト変更が原因」と特定
  損失：2週間でサポートコスト +180万円（人間エスカレーション増加）

Observabilityがあった場合：
  2/1：システムプロンプト変更を検知
  → 「変更前後で回答の一致率が15%低下」をSlackに自動通知
  → 翌日にロールバック判断
  損失：1日分 +約13万円
```

### 評価指標の種類（日本語対応の課題）

| 指標 | 内容 | 日本語対応状況 |
|------|------|-------------|
| **Faithfulness** | 回答がソース文書と整合しているか | グローバルツールで対応可 |
| **Answer Relevance** | 質問と回答が関連しているか | グローバルツールで対応可 |
| **Context Precision** | 正しいコンテキストを取得できているか | グローバルツールで対応可 |
| **日本語文体評価** | 敬語・丁寧語・専門用語の適切さ | **グローバルツールでは対応不可** |
| **有害表現検出（日本語）** | 差別表現・不適切表現の日本語検出 | **グローバルツールでは対応不可** |

**→「日本語LLMの品質をどう測るか」は現時点でグローバルツールが弱い領域。受託事業での差別化ポイントになりうる。**
