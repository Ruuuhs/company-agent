## エグゼクティブサマリー

LLM Observability市場は2025〜2029年にCAGR 36.3%で成長する高速拡大市場であり、日本では専門受託プレイヤーがほぼ存在しない空白地帯にある。2026年4月時点で唯一の専門プレイヤーであるcloudpack（KDDIアイレット）はDatadog依存型のサービス設計であり、「ツール非依存 × オンプレ/プライベートクラウド対応 × OSS活用のスモールスタート型」という軸で明確な差別化が可能である。参入ウィンドウは2026〜2027年の18ヶ月に集中している。小さなチームで技術発信とリファレンスアーキテクチャを整備し、初期3〜5社の実績を積んで先行者ブランドを確立することが最優先課題である。収益化は1社目の受注（目標: 創業3〜6ヶ月以内）から始め、Year1のARRを2,400万〜4,800万円に設定する。

## 1. 解決する課題（ユーザーの痛み）

### ターゲットユーザー（主要ペルソナ）

**ペルソナA: 中堅IT企業の技術責任者（CTO / 技術部長）**
- 会社規模: 従業員50〜500名
- 状況: 社内でLLMを使った業務改善ツール・顧客向けAIサービスを本番稼働させている
- 困っていること: 「LLMが本番で時々おかしな回答を返す。なぜそうなったか追えない。コストも把握できていない。Datadogを使おうとしたが高すぎて稟議が通らなかった。」
- 意思決定スピード: 速い（3〜6ヶ月でPoC→本番判断）

**ペルソナB: 金融・製造業の情報システム部門マネージャー**
- 会社規模: 従業員1,000名以上
- 状況: 機密データを扱うためAzure OpenAIやAWS Bedrockに機密情報を送ることに法務部門が難色を示しており、オンプレLLMを検討・構築中
- 困っていること: 「オンプレでLLMを動かしたいが、クラウドSaaSのObservabilityが使えない。社内に知見がなく、どこに相談すればいいかわからない。」
- 意思決定スピード: 遅い（6〜12ヶ月の検討期間）だが案件単価が大きい

**ユーザーは本当にこれを求めているか？**

根拠1（市場データ）: 日本企業の生成AI導入率は64.4%（日経BP、2024年9月）に達しているが、「期待を上回る効果を実感している企業は限定的」（PwC Japan 2025）というギャップが存在する。本番運用移行後のQuality Assuranceニーズは未充足である。

根拠2（競合の動き）: cloudpackが2026年3月にようやく専門サービスを開始したことは、市場の需要顕在化を示す先行指標である。供給側が動き始めた事実は、需要が確実に存在することの反証である。

根拠3（技術コミュニティ）: CyberAgent・Classmethod・NTTデータTechが2025〜2026年にLLM Observabilityの技術ブログを公表している。エンジニアが「やり方を知りたい」と情報収集しているフェーズであり、「プロに頼みたい」という段階に移行しつつある。

**課題の深刻度**: 高

LLMの非決定論的出力は「正常稼働していても誤答を返す」という従来の監視ツールが対応できない構造的問題を抱えている。本番運用が拡大するほどビジネスリスクが高まり、Observabilityは「あれば便利」から「なければ問題が起きても気づけない」インフラへと昇格している。

## 2. 解決策と価値提案

**ソリューション概要**:

LLM本番システムの「見えない問題」を可視化・定量化し、受託で構築・運用支援する。具体的には、OSSスタック（Langfuse + ClickHouse + OpenTelemetry + Grafana）を基盤とし、顧客のオンプレ・プライベートクラウド環境にセルフホスト型のObservabilityスタックを設計・実装する。特定のSaaSベンダーに依存しないアーキテクチャ設計を提供する。

**提供価値（ユーザーが得られること）**:

- LLMの出力品質・コスト・レイテンシをリアルタイムで把握できる
- ハルシネーションや品質劣化の発生を即座に検知・アラートできる
- 機密データを外部SaaSに送らずにObservabilityを実現できる
- DatadogなどのSaaS前提ツールの1/5〜1/10のコストで同等の監視体制を構築できる
- 日本語LLMの品質を日本語文脈に適した評価指標で継続的に測定できる

**競合との差別化（なぜ自社がやるべきか）**:

| 比較軸 | cloudpack（唯一の競合） | 大手SIer | 自社 |
|--------|----------------------|---------|------|
| ツール依存 | Datadog依存 | 汎用的 | ツール非依存の中立アドバイザリー |
| オンプレ対応 | SaaS前提 | 対応可だが高コスト | OSS活用でオンプレ専門対応 |
| コスト感 | 大企業向け価格帯 | 大企業向け価格帯 | 中堅・スタートアップ向けスモールスタート |
| スピード | 大企業プロセス | 重厚・遅い | 小規模チームで高速実行 |
| 技術発信 | 限定的 | 限定的 | Zenn/Qiita/GitHubで継続的発信 |

自社がやるべき理由: 業界垂直知識がなくても、「LLM Observabilityという水平技術の専門家」として差別化できる。垂直知識を持たないことは弱みではなく、特定ベンダーや業界に縛られない「中立性」という強みに変換できる。

## 5. MVPサービス設計と検証計画

### MVP（最小検証単位）

**「LLM Observabilityクイックスタート診断パッケージ」（50万円/件、工期4週間）**

最初から大型の構築案件を狙わない。まず「現状診断 + OSS構成の提案書」という小さいパッケージで市場に出る。これにより以下を同時に検証できる。

提供内容:
1. 顧客のLLMシステム現状インタビュー（1〜2回、各2時間）
2. 現行の可観測性の空白箇所の特定（レポート提出）
3. OSSスタック構成案の提案（Langfuse + OpenTelemetry + Grafana）
4. 次フェーズ（本構築）のスコープ・価格見積もり提示

このパッケージを初期3〜5社に提供し、「顧客は診断に対価を払うか」「提案からの受注転換率はどれくらいか」を確認する。

### 最初の1件をどう獲得するか

以下の3つのアプローチを並行して実施する。

**チャネル1（0〜1ヶ月）: 代表・創業チームの個人ネットワーク**
既存の知人・元同僚・SNSのフォロワーに直接声をかけ、無償または大幅ディスカウントで最初のケースを獲得する。最初の1件は「実績と事例」を得ることを優先し、価格は二の次にする。

**チャネル2（1〜3ヶ月）: Zenn/Qiitaへの技術記事投稿**
「LLMアプリにLangfuseでObservabilityを構築してみた」「vLLM + Grafana でオンプレLLMを監視する構成」などの実装記事を週1本ペースで公開する。記事末尾に「相談受付」のリンクを設置する。

**チャネル3（2〜4ヶ月）: 技術勉強会・MLOps Connpassへの登壇**
LLMOps・MLOps系の勉強会に発表者として参加し、LLM Observabilityの「実装ノウハウ」を発信する。参加者との名刺交換・SNS接続を通じてリード獲得につなぐ。

### MVP検証のKPI

| KPI | 目標値 | 計測期間 |
|-----|--------|---------|
| 診断パッケージの問い合わせ数 | 月3件以上 | 3〜6ヶ月目 |
| 診断パッケージ受注数 | 3ヶ月で3件 | 創業〜6ヶ月 |
| 診断→本構築への転換率 | 50%以上 | 診断完了後3ヶ月以内 |
| 技術記事の月間PV | 10,000PV以上/月 | 3ヶ月目時点 |
| 問い合わせの自社起因比率 | コンテンツ経由50%以上 | 6ヶ月目時点 |

**成功の定義（次フェーズ移行条件）**: 6ヶ月以内に有償案件3件受注 かつ 1件の本構築案件(150万円以上)受注

## 7. Go-to-Market戦略

### 顧客獲得チャネル（優先順位順）

**第1優先: 創業チームの個人ネットワーク（0〜6ヶ月）**

最もROIが高い初期チャネル。元職場・知人・SNSフォロワーへの直接アプローチ。「試してみてほしい」という形で無償または低価格でのトライアルから入る。目標: 最初の有償案件1〜2件をここから獲得する。

**第2優先: コンテンツマーケティング（Zenn/Qiita/GitHub）（1〜18ヶ月）**

日本国内でLLM Observabilityの「公開されている日本語技術情報」が圧倒的に少ない現状が差別化のチャンスである。以下のコンテンツ戦略を実行する。

| コンテンツ種別 | 媒体 | 頻度 | テーマ例 |
|-------------|------|------|---------|
| 実装解説記事 | Zenn | 週1本 | 「Langfuse v3をDockerでセルフホストする手順」「vLLM + Prometheus + Grafana でオンプレLLMを監視する」 |
| 評価フレームワーク解説 | Qiita | 月2本 | 「日本語LLMの品質評価にRAGASを使ってみた」「LLM-as-Judgeの実装と注意点」 |
| リファレンスアーキテクチャ | GitHub | 随時 | OSSスタック構成のリポジトリ公開（MIT License） |

## 9. リスクと対応策

| リスク | 発生確率 | 影響度 | 具体的な対応策 |
|-------|---------|-------|-------------|
| **大手SIer（NTTデータ・NRI等）の早期参入** | 中 | 高 | 参入前に中堅・スタートアップ向けの事例と技術ブランドを確立。大手が来る前にニッチポジションを固める。大手がターゲットとしない「中堅企業・スタートアップ・低単価スモールスタート」のセグメントに集中する |
| **cloudpackがOSS / オンプレ対応にピボット** | 低〜中 | 高 | 技術発信の蓄積（GitHub Star・記事ストック）がある限り後発への防衛策となる。日本語評価・ツール非依存アドバイザリーの専門性を強化し差別化軸を増やす |
| **OSSスタックのコモディティ化（ツールが標準機能化する）** | 中 | 中 | 「ツールの操作知識」ではなく「Observabilityのアーキテクチャ設計思想」と「業種特化の評価設計」を中核ケイパビリティに置く。ツールは差し替え可能な部品として扱う |
| **技術変化（LLMエコシステムの急速な変化）** | 高 | 中 | 特定フレームワーク（例: LangChain）への過度な依存を避け、OTel標準とアーキテクチャ層の知識を優先する。フレームワークは「実装手段」、OTel + 評価設計思想が「本体」という位置づけを維持する |
| **初期案件が獲得できない（市場の外れ値リスク）** | 低〜中 | 高 | 最初の1〜2社は無償または50%ディスカウントで実績を作ることを許容する。診断パッケージを50万円以下まで下げてでも最初の有償受注を優先する |
| **人材確保困難（LLMOps人材の枯渇）** | 高 | 高 | 採用を「LLMOps経験者」に限定しない。「Pythonが書けて学習意欲が高い」エンジニアを採用し、OJTで育てる方針を取る。GitHubへの技術発信が採用ブランドとしても機能する |
| **顧客がPoCループから抜け出せない（本番移行しない）** | 中 | 中 | 「PoC段階からObservabilityを入れることのメリット」を訴求。診断パッケージをPoC段階から提案できるよう価格・スコープを柔軟に設計する |

### ピボットトリガー（方向転換の判断基準）

以下のいずれかが発生した場合、事業方向性のピボットを代表と協議する。

| トリガー | 判断時期 | ピボット候補 |
|---------|---------|------------|
| 6ヶ月時点で有償案件が1件も取れない | 6ヶ月目 | 対象顧客をスタートアップから大手企業にシフト / 完全無償でエバンジェリスト戦略にシフト |
| 診断→本構築の転換率が10%以下（診断で終わって次につながらない） | 8ヶ月目 | 診断パッケージを廃止し、本構築から直接入るモデルへ変更 |
| cloudpackがOSSスタック対応を開始し直接競合化する | 随時 | 特定業種（金融 or 製造）への業界特化にシフトし競合回避 |
| LLM Observabilityの大手SaaSが日本語UI・日本語サポートを大幅強化し自社の提案余地がなくなる | 随時 | LLM Observabilityの「実装支援」から「評価設計コンサル」のピュアアドバイザリーへシフト |
