## 戦略の結論

# 第2章：Observabilityとはなにか — この領域を抑える意味

## 2-1. Obsの定義

LLM Observabilityとは「AIが何をしているか、なぜそう動いたかを追跡・把握できる仕組み」。従来のAPMが「サーバーが落ちていないか」を見るのに対し、LLM Obsは「回答が正しいか」まで踏み込む。

| 従来APM | LLM Observability |
|---------|------------------|
| 同じ入力 = 同じ出力 | 同じ入力でも毎回異なる出力 |
| エラーコードで判定 | 意味的品質で判定 |
| レイテンシ・エラー率 | ハルシネーション率・品質スコア・コスト |

## 2-2. LLM Obsで見るもの

4つのシグナル：**メトリクス**（異常検知）→ **トレース**（原因追跡）→ **ログ**（証拠保全）→ **評価**（品質採点）

主要KPI：ハルシネーション率（オープン形式で40〜80%）、品質スコア、TTFT、コスト/リクエスト

## 2-3. なぜ今抑えるのか

**① LLMは作った後が重要**: 監視なしで6ヶ月放置するとエラー率35%増加。5ヶ月後にF1スコアが7.4pt低下した追跡調査あり。

**② 品質保証市場は確実にくる**: Gartnerが「2028年にGenAIの50%でObs投資」と予測（現在15%）。3年で3倍以上の市場拡大。

**③ 日本の規制が監視義務化に向かっている**:
- FISC第13版（2025年3月施行済み）: AI安全対策基準を新設
- 金融庁DP v1.1（2026年3月）: 出力データの常時モニタリング態勢を推奨
- ISMAP改訂（2027年3月施行予定）: AI固有管理策の追加見通し

→ 詳細: `15_Obs定義と抑える意味.md`

# 第3章：Agent x OBS — なぜセットでやるのか

## 3-1. Agentの特殊性：動くから監視が必須

AIエージェントは従来のLLMアプリと根本的に異なる。自律的な判断・ツール呼び出し・マルチステップ実行により、**監視なしでは「コスト爆発」「権限逸脱」「品質のサイレント劣化」が不可避**。

- 本番エージェントの**94%**がObservabilityを導入済み（LangChain調査 N=1,340）
- エージェント障害591件中**88%はインフラの欠如（ガードレール・監視の不備）**が原因

## 3-2. AgentにObsがないとどうなるか

**Replit事件（2025年7月）**: AIエージェントが本番DBを全消去。1,206名のデータ消失。
**Klarna事件（2024-2025年）**: AIがCS担当700名を代替 → CSATが22%低下するまで気づけず → CEO「やりすぎた」と方針転換。

## 3-3. 提案の構え：「品質を数字で保証する受託」

IBMの調査で**45%のエグゼクティブが「可視性の欠如」をエージェント統合の最大障壁**と回答。79%が採用しているが本番稼働は11%。この68ptのギャップが商機。

## 3-4. 3つの接点：普通の受託との決定的な差

| 接点 | 通常の受託 | 当社モデル |
|------|---------|----------|
| ①構築時 | 動くかテスト | 品質ベースライン設定・ガードレール設計 |
| ②納品時 | 「動作確認完了」 | 数値ベースの品質証明書を添付 |
| ③運用時 | 保守契約があれば障害対応 | 月次品質レポート・劣化の事前検知 |

## 3-5. セット営業の強み

Agent構築費（フロー収入）+ 月次品質保証運用（MRR）の組み合わせ。チャーン率5%→3%改善でLTVは67%向上（SaaS業界知見）。

## 3-6. なぜAgent構築の会社がObsも提供するのが正しいか

- Obsツール専業ベンダーは「何が起きたか」は分かるが「なぜ起きたか」が分からない
- 品質の「正解」はビジネスロジックと不可分 → 構築者のみが定義できる
- 横串Obs専業は3条件不成立（セルフサーブ・客観品質・同質バイヤー）で成立しない

→ 詳細: `16_AgentxOBS_セット戦略.md`

# 第5章：横串戦略の構造と限界 — なぜセミ縦串を採るのか

## 横串が成立しない3つの理由

| 条件 | Datadog（成立） | LLM Obs受託（崩壊） |
|------|---------------|-------------------|
| セルフサーブ | エージェント1行で完結 | 設計・カスタマイズが必須 |
| 客観品質 | CPU率は普遍 | 品質定義が業界・用途ごとに異なる |
| 同質バイヤー | SRE+EM（業界共通） | CISO・DX部長・情報主幹（業界別に異質） |

## セミ縦串の設計

横串の技術力で入り、縦串の業界理解を段階的に蓄積する。

- Phase 1: 横串80%/縦串20% → Obs技術で最初のセグメントに集中
- Phase 2: 横串60%/縦串40% → 実績が縦串知識に転換
- Phase 3: 横串40%/縦串60% → 専門家として認識される

先行事例: Palantir（データ分析 × 国防）、Veeva Systems（Salesforce × 製薬）

## なぜ「Obsは腕前の証明」か

- Langfuse OSSは無料。「導入します」では価値にならない
- 価値は「何を測るか」の設計 ×「どう測るか」の実装 ×「結果をどう解釈するか」の判断
- ツールのコモディティ化が進むほど「設計・実装できる人間」の希少性が上がる

→ 詳細: `19_横串戦略の限界とセミ縦串.md`

# 第9章：技術戦略

## 3つの技術原則

1. **OSSファースト**: Langfuse + OpenTelemetry + RAGAS。顧客のデータ主権とコスト効率を同時に担保
2. **標準準拠**: OpenTelemetry GenAI SIGに先行実装。ベンダーロックイン回避
3. **日本語評価エンジンの自社開発**: 敬語・法規制・曖昧表現の評価。グローバルに存在しない唯一の参入障壁

## 推奨技術スタック

```
計装: OpenTelemetry SDK + openllmetry
トレース: Langfuse v3（MIT・ClickHouse傘下）
評価: LLM-as-Judge + RAGAS + DeepEval + 自社日本語評価
ガードレール: NeMo Guardrails + LlamaFirewall
データ: ClickHouse + PostgreSQL
可視化: Grafana + Prometheus
```

# 第10章：将来構想 — ISMAP/FISC対応のLLM品質管理SaaS

## 3段階の進化シナリオ

```
Phase A（1〜2年目）: 受託専業
  → 案件ごとに品質保証基盤を構築。評価テンプレート・ベンチマークデータを蓄積

Phase B（2〜3年目）: ハイブリッド（受託 + プロダクト）
  → 蓄積したテンプレートをSaaSとして提供開始。受託はプレミアム案件に集中

Phase C（3〜5年目）: プロダクト主体
  → ISMAP-LIU取得。「LLM品質管理SaaS」として政府・金融市場への唯一の選択肢に
```

## 戦略的資産

- **JLM-Bench（Japan LLM Quality Benchmark）**: 受託案件の匿名化データから業界別品質ベンチマークを構築
- **業界別評価テンプレートライブラリ**: 金融・官公庁・製造の規制対応済み評価セットを資産化
- **ISMAP-LIU取得（2027-2028年目標）**: LLM品質管理でISMAP登録SaaSは現在ゼロ。先に取得した会社が唯一の選択肢に

→ 詳細: `21_技術戦略_将来構想.md`

# 第12章：リスクと対策

## 最重要リスク（Sランク・即時対応）

| リスク | 影響度 | 対策の核心 |
|--------|--------|----------|
| 大手SIer参入（1〜2年以内） | 高 | 参入ウィンドウ内に3〜5件の実績確立。中堅向けスモールスタート枠で差別化 |
| LLMOps×Obs横断人材の採用難 | 高 | 技術発信による採用ブランド構築。内製化支援サービスを通じた人材パイプライン |
| PoC→本番移行停滞 | 高 | 「品質が不安で本番に上げられない」をObs品質可視化で解決。規制を営業トリガーに活用 |
| 大企業商談の長期化 | 高 | アセスメント（100万円・4週間）をフロント商品にキャッシュフロー確保 |
| 初期実績ゼロでの営業難 | 高 | Zenn/Qiita技術記事での信頼獲得。モニター価格（70-80%）での初期案件 |
| 創業者依存 | 高 | 品質保証プロセスの文書化・テンプレート化で属人性を排除 |

## 全リスクを貫く対応軸

**「ツール非依存の設計知識・業界特化の評価指標・品質の数値証明能力」を中核に置く**。この軸がすべてのリスクカテゴリに対して一貫して有効。
