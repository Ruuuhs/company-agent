# 第5章：横串戦略の構造と限界 — なぜセミ縦串を採るのか

**作成日**: 2026-04-30
**担当**: 戦略立案者（経営企画部）

---

## エグゼクティブサマリー

横串戦略が崩れる構造的理由は3つ——セルフサーブ不可能・客観品質の不在・バイヤーの異質性。セミ縦串（横串の技術力 × 縦串の業界理解のハイブリッド）を採用し、Obsを「商品」ではなく「腕前の証明」として位置づけることが最も正しい。

---

## 5-1. 横串戦略の構造

### 横串成立の3条件

| 条件 | 定義 | 崩壊時に起きること |
|------|------|------------------|
| セルフサーブ可能性 | 顧客が自分で導入・運用完結 | CSコスト爆増 |
| 客観的品質指標 | 誰が測っても同じ結果 | 横断的な比較・売りが不可能 |
| 同質バイヤー | 業界問わず同じ購買パターン | 営業方程式が統一不能 |

### 成功事例との対比

- **Datadog**: エージェント1行インストール、CPU率等の普遍指標、SRE+EMが業界共通で評価 → 年間$2B超
- **Stripe**: API実装で完結、決済成功率が普遍指標 → 全業界に水平展開

---

## 5-2. LLM Obsで横串が成立しない理由

### 崩壊①：セルフサーブの限界

| ステップ | セルフサーブが困難な理由 |
|---------|----------------------|
| ツール選定 | 顧客環境に依存 |
| インフラ設計 | 規制環境・データ主権ルールで判断が変わる |
| 評価指標設計 | 「何をもって品質が良いか」をシステムごとに定義が必要 |
| PIIフィルタリング | 法務判断を要する |

### 崩壊②：客観的品質指標の不在

- 金融FAQ → 「法令解釈の正確性」が品質
- 製造保全 → 「異常検知の精度」が品質
- EC商品説明 → 「コンバージョン貢献」が品質

→ 「良いLLM」の定義が業務文脈に埋め込まれている

### 崩壊③：同質バイヤーの不在

| 業界 | 意思決定者 | 承認プロセス |
|------|----------|------------|
| 金融 | CISO / リスク管理部長 | 半年〜1年の稟議 |
| 官公庁 | 情報システム部長 | 入札手続き |
| 製造 | DX推進部長 / CTO | 数ヶ月の評価 |
| スタートアップ | CTO | 即断（1〜2週間） |

## 5-3. セミ縦串戦略の設計

### 先行事例

| 企業 | 横串要素 | 縦串要素 | 結果 |
|------|--------|--------|------|
| Palantir | データ分析基盤 | 国防・金融の業務フロー理解 | 高単価・長期契約で上場 |
| Veeva Systems | Salesforceベースのクラウド | 製薬・ライフサイエンス特化 | 時価総額$30B超 |
| **当社（設計中）** | LLM Obs技術 | 官公庁→金融→製造（段階的） | 規制×Obsで参入障壁構築 |

### 時間的変化（動的設計）

```
Phase 1（参入期）: 横串80% / 縦串20% → Obs技術で最初のセグメントに集中
Phase 2（定着期）: 横串60% / 縦串40% → 実績が縦串知識に転換
Phase 3（確立期）: 横串40% / 縦串60% → 専門家として認識される
```

## 5-4. なぜ「Obsは商品ではなく腕前の証明」が正しいか

### ツールを売る戦略の構造的限界

| ツール | 価格 |
|--------|------|
| Langfuse OSS | 無料（MIT License） |
| Langfuse Cloud | Hobbyプラン無料 |
| Datadog LLM Obs | 既存契約のアドオン |
| New Relic | 無料枠あり |

→ 「Langfuseを導入します」では価値にならない

### 「腕前の証明」の3要素

1. **「何を測るか」の設計知識**: 業界・規制ごとに評価指標を定義できる
2. **「どう測るか」の実装知識**: LLM-as-Judge・RAGAS日本語適用・PII設計
3. **「測った結果をどう解釈するか」の判断知識**: ハルシネーション率3%が許容かは用途次第

→ ツールのコモディティ化が進むほど「設計・実装できる人間」の希少性が上がる

## 5-5. 普通の受託との決定的な差

| 比較軸 | 一般的なAI受託 | 当社（Obs付き品質保証受託） |
|-------|-------------|------------------------|
| ゴール | 動くシステムを作る | 品質基準を継続して満たす状態を作る |
| 成果物 | コード + 仕様書 | コード + 品質基準書 + 測定基盤 + 月次レポート |
| 納品の定義 | 「構築完了」 | 「品質が数値で証明できる状態」 |
| 運用後 | 保守があれば障害対応 | 月次品質数値を提供し続ける |
| 解約しにくさ | 保守終了で関係終了 | 「品質の証明」停止への不安が継続を促す |

### 収益の重心変化（仮説）

```
Year 1: フロー80% / ストック20%
Year 2: フロー60% / ストック40%
Year 3: フロー40% / ストック60% → 事業安定性が増す
```

## 第5章まとめ

| 論点 | 回答 |
|------|------|
| 横串が成立しない理由 | セルフサーブ・客観品質・同質バイヤーの3条件がすべて崩壊 |
| なぜ「Obsは腕前の証明」か | ツールは無料化。価値は「設計・実装・継続証明できる能力」 |
| 普通の受託との差 | 3接点（構築・納品・運用）すべてに品質数値化が介在しストック収益へ接続 |
