## 2. 競合環境 — 誰がいて、何が空いているか

### 大手プラットフォーム（9社全て参入済み）
- Datadog, New Relic, Dynatrace, Splunk, Elastic, Grafana, AWS, Azure, Google
- **共通の弱点**: 「既存APMへのLLM機能追加」であり、LLM品質評価（ハルシネーション検知等）の深度が浅い

### スタートアップ（資金調達が活況）
- LangChain（$1.25Bユニコーン）、Arize AI（$70M Series C）、Braintrust（$80M Series B）
- **構造変化**: LangfuseがClickHouseに買収、HumanloopがAnthropicに買収→M&A加速
- OSSファーストが市場標準。エージェント監視が次の主戦場

### 日本国内
- **cloudpack（KDDIアイレット）がほぼ唯一の専門プレイヤー**（2026年3月サービス開始）
- cloudpackはDatadog依存型 → **オンプレ・ツール非依存が空白地帯**
- 大手SIer（NTTデータ, NRI, アクセンチュア）はObservability特化サービス未展開

## 3. 規制環境 — 追い風が吹いている

### FISC・金融庁（金融機関向け）

| 規制・基準 | 内容 | LLM Observabilityとの関連 |
|-----------|------|------------------------|
| **FISC安全対策基準 第13版**（2025年3月） | AI安全対策基準を新設。AI利活用の方針策定・運用管理・安全対策・教育の4カテゴリ | プロンプト/レスポンスのログ管理・品質監視・異常検知が基準項目に直結 |
| **金融庁AIディスカッションペーパー v1.1**（2026年3月） | モデルリスク管理・サードパーティリスク・PII保護・プロンプトインジェクション対策 | 4領域すべてがObservability機能で対応可能 |
| **金融庁AI官民フォーラム** | リスク管理を協調領域として業界横断で知見共有 | 標準化されたObservability基盤の需要を示唆 |

### ISMAP・デジタル庁（官公庁向け）

| 規制・基準 | 内容 | LLM Observabilityとの関連 |
|-----------|------|------------------------|
| **デジタル庁DS-920ガイドライン**（2025年5月） | 政府調達の事実上の標準。調達チェックシートに「有害情報の出力制御」「ログ保存」「ハルシネーション対策」を明記 | 受注の前提条件としてObservability対応実績が必要に |
| **ISMAP管理基準改訂**（2027年3月施行予定） | AI固有の管理策が追加される見通し | Observabilityツールのセキュリティ基準対応が求められる |
| **国産LLM「源内」7選**（2026年3月確定） | 2026年8月から全府省庁18万人規模の実証開始 | 実証開始後にObservability整備案件が急増する見通し |

### ISO/JIS（国際・国内標準）

| 規制・基準 | 内容 | LLM Observabilityとの関連 |
|-----------|------|------------------------|
| **JIS Q 42001:2025**（ISO/IEC 42001のJIS化、2025年8月） | AI管理システムの認証規格。国内初認証事例あり | 認証取得支援 = Observabilityを「証跡管理システム」として高単価提案可能 |
| **AI事業者ガイドライン v1.1**（総務省・経産省、2025年3月） | 透明性・説明可能性・公平性の確保を要求 | LLMの判断根拠の記録・監査がObservabilityの機能領域 |

**一言**: 規制が「LLM Observabilityは導入すべき」から **「導入しなければ調達・監査に通らない」** へと変わりつつある。特にFISC第13版とDS-920は、受託事業の営業において「なぜ必要か」を説明する最強の根拠になる。

## 4. 最大の機会 — なぜ勝てるのか

### 空白地帯マップ

```
                  クラウドSaaS ←──────────→ オンプレ/セルフホスト
                       │                         │
    大手APMベンダー ────┤                         │
    cloudpack ─────────┤                         │
                       │                         │
                       │              ★ ここが空白 ★
                       │              金融・官公庁・製造業が
                       │              データを外部に出せない
```

### なぜこの空白が埋まっていないのか

- cloudpackはDatadog（SaaS）前提 → データ外部送信不可の顧客に対応できない
- 大手SIerは汎用AI導入支援に注力 → Observability専門サービスは未展開
- グローバルOSSツールは日本語評価・FISC/ISMAP対応が手薄

---

### 差別化の4本柱（規制対応を追加）

1. **オンプレ/プライベートクラウド専門**: Langfuse OSS + ClickHouse + OpenTelemetry + Grafanaのセルフホスト構築。cloudpack（Datadog依存）と真逆のポジション
2. **ツール非依存の中立アドバイザリー**: 顧客の既存スタックに応じた最適ツール選定
3. **日本語特化の品質評価**: 敬語・文体一貫性・法規制（景表法・薬機法等）対応の評価設計
4. **FISC/ISMAP/DS-920準拠支援**: 規制要件に対応したログ設計・監査証跡・PII検知を標準装備（**NEW**）

## 5. 推奨戦略: オプションA「オンプレ/ハイブリッドLLM Observability専門」

### なぜA案か（3つのオプション中の推奨理由）

| オプション | ポジショニング | 3年目売上ポテンシャル | 推奨度 |
|-----------|-------------|-------------------|-------|
| **A: オンプレ専門（推奨）** | 金融・官公庁・製造業向けセルフホスト構築 | 2.4〜3.4億円 | ★★★ |
| B: 日本語品質評価特化 | 日本語LLM評価・ガードレール設計 | 5,600万〜1.1億円 | ★★ |
| C: SME向けパッケージ | 中小企業向けOSS標準化 | 7,500万〜1.4億円 | ★ |

**A案を推奨する理由**:
1. 空白地帯の競争優位が最も鮮明（cloudpackは構造的に対応不可）
2. 高単価（構築300〜800万円）× ストック収益（運用月額50〜150万円）の両立
3. オンプレという技術的参入障壁が先行者優位の時間的余裕を生む

## 8. リスクと対策

| リスク | 影響度 | 対策 |
|--------|--------|------|
| 市場成熟（3〜5年でツール標準機能化） | 高 | ストック収益（運用代行）を積み上げ、ツール変化に左右されない顧客基盤を構築 |
| 大手SIer参入（1〜2年以内） | 中 | オンプレ専門という技術的参入障壁 + 事例・ブランドの先行蓄積 |
| 技術変化（6〜12ヶ月サイクル） | 高 | ツール非依存のアーキテクチャ知見を核に。個別ツールは差し替え可能な設計 |
| 人材確保 | 高 | 技術発信による採用ブランド構築。内製化支援サービスを通じた人材パイプライン |
| 大企業の商談長期化（6〜12ヶ月） | 中 | 診断パッケージ（小口）をフロントに置き、キャッシュフローを確保 |
