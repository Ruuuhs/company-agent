**対象**: AIエージェント構築・Observability品質保証受託事業（新規立ち上げ）

## エグゼクティブサマリー

本書は社長向けレポートの第6章「事業コンセプト」・第7章「ターゲット顧客」・第8章「収益モデル」を収益設計者の視点で設計したものである。

**設計の3つの核心**:

1. 事業の本質をObservabilityツール提供から「AIエージェントの品質を数字で保証する構築・運用サービス」に再定義する。これにより既存Obs受託と完全に差別化され、価格プレミアムの根拠が明確になる。

2. ターゲットは「官公庁→金融→製造」の段階的展開を前提とし、1年目は金融・IT SaaSに集中してICPを確立する。官公庁は参入に9〜18ヶ月かかるため2年目以降の主戦場とする。

3. 標準シナリオで3年目年間売上2.4億円・営業利益率32%・MRR比率55%以上を目標とする。ユニットエコノミクスはLTV/CAC比15〜25倍で成立する（仮定）。

**代表への意思決定依頼**: 本書末尾「第8章 判断のお願い」を参照。価格設定・資金調達方針について2026年5月末までに確定が必要。

# 第6章: 事業コンセプト

---

## 6.1 コンセプト文（一文）

**「AIエージェントが正しく動いているかを数字で証明し、品質に責任を持つ構築・運用パートナー」**

この一文が示すものは3つである。

| 要素 | 意味 | 競合との違い |
|------|------|------------|
| 「数字で証明する」 | 品質をスコアとして可視化・報告する | 「動いている」の感覚値で終わらない |
| 「品質に責任を持つ」 | 構築して終わりでなく運用まで継続する | PoC止まりのコンサルと異なる |
| 「構築・運用パートナー」 | 一体型サービスとして提供する | ObsツールSIと構築SIが別々の現状を統合する |

---

## 6.2 ポジショニングステートメント

**「我々は、本番稼働するAIエージェントの品質を継続的に保証したい企業のための、唯一の構築・運用一体型専門パートナーである。」**

### 補足説明（社内向け）

| 要素 | 内容 |
|------|------|
| 誰のための | 本番稼働するAIエージェントを持つ中堅〜大手企業 |
| 何を提供するか | 品質保証付きのAgent構築と継続的Obsによる運用 |
| 競合と何が違うか | 構築とObs品質保証が分離していない一体型 |
| なぜ信頼できるか | 業種固有のガードレール・オンプレ対応・ツール非依存 |

### ポジショニングマップ

```
             「品質保証まで責任を持つ」
                        |
  大手SIer（NTTデータ等）|
  コンサル（高価格・汎用） |
                        |
  ←─────────────────────┼─────────────────────→
  「Agent構築のみ」      |            「Obs+Agent一体型」
  （PoC・単発）          |
                        |   ★ 自社ポジション
                        |   （Agent構築+品質保証運用
                        |    の一体型・中価格帯）
                        |
  cloudpack・Datadog系  |
  （Obsツール提供SaaS依存）|
                        |
             「ツール提供・監視のみ」
```

## 6.3 既存Obs受託サービスとの違いの明確化

### なぜ「横串ObsサービスSI」では成立しないか

調査で判明した3条件の不成立から、既存フレーミングを廃棄する必要がある。

| 不成立条件 | 内容 | 影響 |
|-----------|------|------|
| セルフサーブ不成立 | Obs単体では顧客が自己調達を試みる | 受注単価・継続率が低くなる |
| 客観品質不成立 | 「Obsを入れた」ことが成果になりにくい | 成果指標が曖昧で解約リスクが高い |
| 同質バイヤー不成立 | 購買者がCTO/エンジニアで予算決裁が難しい | 予算化のハードルが高く商談が長くなる |

### 新フレーミングで何が変わるか

| 比較軸 | 旧フレーミング（Obs受託） | 新フレーミング（Agent+品質保証） |
|--------|----------------------|-------------------------------|
| 売り文句 | 「LLM Observabilityを構築します」 | 「AIエージェントの品質を数字で保証します」 |
| バイヤー | CTOまたはエンジニアリードのみ | DX推進部・事業部門も予算を持てる |
| 成果の見せ方 | 「Grafanaダッシュボードができました」 | 「品質スコアが前月比+15%改善しました」 |
| 解約リスク | Obs不要と思われたら即解約 | 品質が下がった時に「なくせない」 |
| 価格根拠 | ツール費用の代替 | ビジネスリスク回避の対価 |

**ObservabilityはProduct（商品）ではなく「腕前の証明」である**。この思想転換こそが、新フレーミングの核心である。

## 7.1 優先セグメントの選定と段階的展開計画

### 展開ロードマップ

| フェーズ | 時期 | 主戦場 | 選定理由 |
|---------|------|--------|---------|
| Phase 1（ICPの確立） | 1年目 | 金融・IT SaaS | 予算決裁が早い・AI本番化が最も進んでいる・参照事例として他業種に波及しやすい |
| Phase 2（垂直展開） | 2年目 | 官公庁・製造 | 官公庁はオンプレ要件でプレミアム価格が成立・参入に9〜18ヶ月の関係構築が必要なため準備を1年目から開始 |
| Phase 3（拡大） | 3年目 | 医療・流通 | Phase 1〜2の業種特化ノウハウを横展開する |

### なぜ官公庁を1年目主戦場にしないか

官公庁は最終的に最高単価・最長継続のセグメントである。しかし以下の理由から「1年目の主戦場」にすることは収益上の誤りである。

1. **調達プロセスに最低9ヶ月**: 一般競争入札・随意契約基準のハードル。1年目の売上にならない。
2. **実績要件**: 過去の類似案件納品実績を求められる。ゼロ実績では参加できない。
3. **キャッシュフローの危機**: 売上ゼロ期間が長くなり、資金ショートリスクが高まる。

**結論**: 官公庁は「1年目から関係を仕込む」対象であり、売上は2年目から本格化させる設計とする。

### ペルソナ1（1年目最優先）: 金融機関のDX推進担当

| 項目 | 内容 |
|------|------|
| 役職 | DXプロジェクト推進室・部長または課長（40〜50代） |
| 所属企業規模 | 地方銀行・中堅証券会社・中堅保険会社（従業員500〜5,000名） |
| 現状の課題 | 行内に試験導入したLLMチャットボット・RAGシステムが本番化されたが「何が起きているか分からない」「コンプライアンス部から品質を証明しろと言われている」 |
| 予算感 | 年間500万〜2,000万円のDXシステム予算枠。ITベンダー案件として稟議が通りやすい。 |
| 購買決定者 | DX推進室長・情報システム部長。IT調達の稟議ルートあり。 |
| 購買のトリガー | コンプライアンス部・監査部からのLLM品質証明要求。または生成AI導入後の誤出力トラブル。 |
| 競合への反応 | SaaSでの外部データ送信はNG（データ主権問題）。オンプレまたはVPC内での対応を必須とする。 |
| 自社への期待 | 「監査対応に使えるレポートを月次でください」「ベンダーと同じことをしているのに自社が分からないでは困る」 |

### ペルソナ2（1年目並行）: SaaS・IT企業のCTO

| 項目 | 内容 |
|------|------|
| 役職 | CTO、または技術部門VP（30〜40代）|
| 所属企業規模 | AI機能を本番提供しているSaaS企業（従業員50〜500名） |
| 現状の課題 | ChatGPT APIを利用した機能を本番リリース済み。「コスト爆発が怖い」「品質劣化をどう検知するか」「ユーザーがどんなプロンプトを送っているか見えない」 |

| 購買決定者 | CTO自身または技術ディレクター |
| 購買のトリガー | LLMコストの月次予算超過。ユーザーからの品質クレーム増加。 |
| 競合への反応 | Datadog等のSaaSは使っているが「LLMのトレースまで追えない」。OSSに興味があるが実装工数がない。 |
| 自社への期待 | 「手を動かさなくて済むようにしてほしい」「スコアが下がったらアラートを飛ばしてほしい」 |

### ペルソナ3（2年目以降）: 官公庁のシステム企画担当

| 項目 | 内容 |
|------|------|
| 役職 | 情報政策課・デジタル推進室の係長〜課長（35〜50代） |

| 予算感 | 単年度予算500万〜3,000万円。複数年度継続は別途承認が必要。 |
| 購買決定者 | 課長〜部長の決裁。金額によって上位決裁が必要。 |
| 購買のトリガー | 国のAI活用ガイドライン改定。議会・監査委員会からの品質説明要求。 |
| 競合への反応 | 大手SIer（NTTデータ・富士通等）との既存関係が強い。サブコン経由でのアクセスが現実的。 |
| 自社への期待 | 「完全オンプレで・外部にデータが出ない構成で・監査に使えるレポートを」 |

| 項目 | 内容 |
|------|------|
| 役職 | 生産技術部・デジタル変革推進部のリード（35〜50代） |
| 所属企業規模 | 中堅〜大手製造業（従業員1,000〜10,000名） |
| 現状の課題 | 設計書・マニュアル検索にRAGを試験導入。「設計ミスに関わる情報の誤出力が怖い」「どこまでの品質なら本番OK か判断できない」 |

| 購買のトリガー | 品質保証部門・法務部門からの品質要件定義要求。 |
| 競合への反応 | 現場系ITベンダーとの関係が強い。AI専門ベンダーは縁遠い。ただし品質が説明できれば上層部も動く。 |

## 7.3 ICP（理想的な顧客像）の定義

LTVとCACを最大化するICP（Ideal Customer Profile）を以下のように定義する。

### ICP定義

**「AIエージェントを本番稼働させており、品質を外部に説明する義務または内部プレッシャーが存在し、オンプレまたはプライベートクラウド環境を要件とする、従業員500名以上の金融・官公庁・製造企業」**

### ICPスコアリング基準（案件評価に使用する）

| 評価項目 | 配点 | 高スコア条件 |
|---------|------|------------|
| AIエージェントが本番稼働中 | 30点 | RAG・チャットボット・自動化Agentが1本以上本番稼働 |
| 品質説明の外部要求あり | 25点 | コンプライアンス・監査・議会・顧客からの品質証明要求 |
| オンプレ・VPC要件あり | 20点 | データ主権規制・社内セキュリティポリシーが外部SaaS禁止 |
| 予算決裁者が特定できる | 15点 | DX推進室・情報システム部が予算を持っている |
| 業種が金融・官公庁・製造 | 10点 | 規制・品質基準が厳格な業種 |

**合計80点以上**: 優先的に営業リソースを投下するICP顧客
**合計50〜79点**: 標準的な営業プロセスで対応するターゲット顧客
**合計49点以下**: 当面は対象外（エンジニアリソース不足のため優先度を下げる）

## 8.1 サービスメニュー（新フレーミング対応版）

旧来の「7サービス（Obs中心）」から「4サービス（Agent+品質保証中心）」に再設計する。各サービスの役割をLTVジャーニーの中で位置づける。

### 顧客ジャーニーとサービスの対応

```
[顧客の状態]           [自社サービス]           [課金モデル]

「まず現状を知りたい」
        ↓
  ── 品質アセスメント ──────────────────  単発フィー（75万〜150万円）
        ↓（50%がコンバート）
「構築してほしい」
        ↓
  ── Agent構築（品質設計込み） ─────────  一括フィー（300万〜1,200万円）
        ↓（80%がランニングへ移行）
「継続して品質を保証してほしい」
        ↓
  ── 品質保証運用（月次MRR） ───────────  月次継続（50万〜120万円/月）
        ↓（30%がアップセル）
「自社でできるようにしたい」
        ↓
  ── 内製化支援 ────────────────────  月次フィー（40万〜80万円/月、3〜6ヶ月）
```

### サービスSV-1（入口商品）: Agent品質アセスメント

**コンセプト**: 「あなたのAIエージェントの今の品質スコアを数字でお見せします」

**内容**: 稼働中または開発中のAIエージェント・LLMシステムに対し、品質観測の現状診断とロードマップ提供。成果物はスコアレポート（20〜30ページ）＋品質保証設計書のドラフト。

旧サービスA（LLM Obs現状アセスメント）からの変更点: フレーミングを「Obsの診断」から「品質スコアの診断」に転換。報告書のメイン指標を「Obsツールの有無」から「品質スコアの現状値と目標値」に変更。

**ターゲット**: ICPスコア50点以上かつAIシステム本番稼働中の企業

**価格設定**:
- 標準（クラウド環境、エージェント1〜3本）: 100万〜150万円
- 大規模（オンプレ・複数システム）: 150万〜250万円
- 根拠: 旧アセスメントの中央値95万円から15〜20%引き上げ。「Obsの診断」より「品質スコアの診断」は提案価値が高く、コンプライアンス対応や監査対応コストとの比較で正当化できる。

**工数（仮定）**: エンジニア1名 × 10〜15人日
**粗利率（仮定）**: テンプレート整備後は55〜70%
**次のアクション設計**: アセスメント報告会で必ず「構築フェーズの概算見積もり」を提示する。コンバート率目標50%。

---

### サービスSV-2（主力・単価最大化）: AIエージェント構築（品質設計込み）

**コンセプト**: 「品質保証の仕組みをAgentに最初から組み込んで構築します」

**内容**: AIエージェント・RAGシステムの設計・構築。ObservabilityスタックをAgentに内包した形で実装する（後付けでなく設計段階から組み込む）。成果物: 稼働するAgentシステム＋品質ダッシュボード＋月次品質レポートのひな形。

旧サービスB（OSS構築）・旧サービスD（オンプレ構築）を統合し、「AgentにObsを組み込む」という一体型に再設計。

**ターゲット**: SV-1完了後の顧客。または他社でAgent構築したがObs品質保証がない企業。

**価格設定**:
- クラウド（AWS/GCP/Azure）構築、エージェント1〜3本: 300万〜500万円
- クラウド＋カスタム品質評価パイプライン＋ガードレール: 500万〜800万円
- オンプレ・完全内部完結・マルチ環境: 700万〜1,200万円
- 根拠（価値ベース）: 旧サービスBの「180〜700万円」から下限を引き上げ。「Obsを後付けする工数」が不要になることと、「品質設計込みの構築」は技術的難易度が高い工程であることを根拠にする。競合の中堅SIer（Agent構築のみ、Obs別途）より最大30%高いが、「品質保証が込み」で総コストは同等以下になる設計。

**工数（仮定）**: エンジニア2名 × 30〜80人日（規模による）
**粗利率（仮定）**: 45〜60%（ツール非依存・テンプレート活用で改善）
**採算最低価格（仮定）**: クラウド案件400万円、オンプレ案件800万円（エンジニア2名・フリーランス活用時）

> 財務コントローラーへの確認依頼: 上記採算ラインはエンジニア業務委託日額4.5〜6万円を仮定した試算。実際の原価確認後に再設定が必要。

---

### サービスSV-3（MRRの核・LTV最大化）: Agent品質保証運用（月次継続）

**コンセプト**: 「毎月、AIエージェントの品質スコアを測定・改善し、経営に報告できる形で届けます」

**内容**: 稼働中Agentの継続監視・月次品質スコアレポート・コスト推移分析・異常検知・改善提案。報告書は「監査・コンプライアンス部に提出できる形式」で設計する。

旧サービスC（月次Observability運用代行）からの変更点: 提供成果物を「監視レポート」から「品質保証証明書」に格上げする。バイヤーを「エンジニアリード」から「DX推進部・コンプライアンス部」に拡大する。

**価格設定（3段階プラン）**:
- ライト（月次品質スコアレポート＋アラート対応のみ）: 月50万円
- スタンダード（レポート＋コスト最適化＋改善提案1件）: 月80万円 ← 中央帯（誘導目標）
- プレミアム（上記＋週次ミーティング＋改善実装2件含む）: 月120万円
- 根拠（心理的価格設定）: 旧サービスCの最低30万円から引き上げ。「品質保証証明書」というフレーミングにより、コンプライアンス・監査対応コスト（弁護士・コンサルへの支払い相場：月50万円〜）との比較で価格が正当化される。3段階設定でスタンダード（80万円）への誘導を設計する。

**工数（仮定）**: エンジニア0.5名（5〜8社担当）
**粗利率（仮定）**: テンプレート自動化後70〜75%（スタンダード80万円での試算）
**最低契約期間**: 6ヶ月（以後自動更新）

---

### サービスSV-4（LTV延長・信頼強化）: Agent内製化支援プログラム

**コンセプト**: 「最終的に自社で品質管理できるチームを育成します」

**内容**: クライアント社内エンジニアへのAgent品質管理スキル移転。ハンズオントレーニング（3〜5日間）＋アーキテクチャレビュー（月2回）＋Slackサポート（3ヶ月）。

## 8.4 ユニットエコノミクス

LTVとCACを計算し、ユニットエコノミクスの成立を確認する。

### LTV計算（標準顧客ジャーニー: SV-1 → SV-2 → SV-3）

| ジャーニーステップ | 金額（仮定） | 備考 |
|---------------|------------|------|
| SV-1: 品質アセスメント | 125万円 | 中央値 |
| SV-2: Agent構築（クラウド標準） | 500万円 | 中央値（仮定） |
| SV-3: 品質保証運用（スタンダード） | 80万円/月 × 30ヶ月 = 2,400万円 | 継続30ヶ月（仮定・年間解約率25%相当） |
| **LTV合計** | **3,025万円/顧客（仮定）** | |

旧設計のLTV（1,885万円）から約60%増加。SV-3の単価引き上げ（60万→80万円）と継続期間の延長（24→30ヶ月）が主な要因。

### LTV計算（高単価顧客ジャーニー: SV-1 → SV-2オンプレ → SV-3プレミアム）

| ジャーニーステップ | 金額（仮定） | 備考 |
|---------------|------------|------|
| SV-1: 品質アセスメント（大規模） | 200万円 | |
| SV-2: オンプレAgent構築 | 900万円 | 中央値（仮定） |
| SV-3: 品質保証運用（プレミアム） | 120万円/月 × 36ヶ月 = 4,320万円 | 官公庁・金融は解約率が低い（仮定・年間解約率15%相当） |
| **LTV合計** | **5,420万円/顧客（仮定）** | |

### CAC計算

| 獲得チャネル | CAC（仮定） | 前提 |
|------------|----------|------|
| 技術ブログ・登壇（インバウンド） | 80万〜120万円/件 | エンジニアの技術発信工数（月10人日）を帰属コストとして計算 |
| クラウドベンダー（APN等）パートナー経由 | 50万〜80万円/件 | 紹介フィーなし・SA紹介ベース |
| 中堅SIerサブコン経由 | 30万〜50万円/件 | マーケコスト不要だが利益率がやや低い |
| 平均CAC（仮定） | 100万円/件 | チャネルミックスを考慮した加重平均 |

### LTV/CAC比の評価

| 顧客タイプ | LTV（仮定） | CAC（仮定） | LTV/CAC比 | 評価 |
|----------|----------|----------|----------|------|
| 標準顧客（クラウド・SaaS） | 3,025万円 | 100万円 | 30.3倍 | 基本ライン（3倍）を大幅超過。ユニットエコノミクス成立 |
| 高単価顧客（オンプレ・金融・官公庁） | 5,420万円 | 100万円 | 54.2倍 | 極めて高い収益性。ただし案件獲得のリードタイムが長い点に注意 |

**LTV > CAC × 3 の基本ラインを大幅に超過。ユニットエコノミクスは成立する（仮定前提）。**

### 黒字化ライン

**月次損益分岐点（仮定: 固定費200万円/月、粗利率60%）**:
- 損益分岐売上 = 200万円 / 0.60 = **月売上 333万円（仮定）**

**333万円の達成条件（新フレーミング）**:
- SV-3（スタンダード80万円）の契約顧客: 4社（月320万円）+ 単発案件按分（月20〜50万円）
- 旧フレーミング（スタンダード60万円）に比べ、**必要顧客数を4〜5社から3〜4社に削減できる**

**月次黒字化タイミング（仮定）**: 1年目の7〜8ヶ月目（SV-3顧客が3〜4社に達した時点）
