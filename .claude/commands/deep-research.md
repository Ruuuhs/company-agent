# /deep-research — 大規模並列市場調査コマンド

## このコマンドの役割

指定されたテーマについて、複数エージェントを段階的・並列に起動し、市場参入の意思決定に必要な情報を網羅的に調査する。
調査結果は `Output/[テーマ名]/` に分割して格納する。

**用途**: 新規事業の参入判断、受託サービスの市場性検証、定期的な市場モニタリング

**前提（自社プロファイル）:**
- AI受託スタートアップ（創業初期）
- 垂直の業界知識ではなく、水平の技術力（LLM関連技術）で勝負する方針
- リファレンス・実績がまだ少ない段階
- 少人数・低コストで始められる案件を最初のターゲットとする

---

## 実行フロー（5フェーズ構成）

```
Phase 1: 調査設計・仮説構築
    ↓
Phase 2: 一次調査（7軸並列）
    ↓
Phase 3: 二次調査・クロス分析（一次調査の深掘り）
    ↓
Phase 4: 統合戦略立案
    ↓
Phase 5: エグゼクティブレポート・意思決定支援
```

---

## Phase 1: 調査設計・仮説構築（チーフが実行）

ユーザーの指示からテーマを特定し、調査の全体設計を行う。
ユーザーが `$ARGUMENTS` でテーマを渡した場合はそれを使う。

### 1-1. 調査設計チェックリスト

| 項目 | 確認内容 |
|------|---------|
| 調査テーマ名 | 出力フォルダ名にも使用。英語表記も決める |
| 調査の目的 | 「参入すべきか判断する」「受託の可能性を検証する」等 |
| 出力先 | デフォルト: `Output/[テーマ名]/` |
| 自社の立ち位置 | 上記「前提」を基本とし、ユーザーが補足すれば反映 |
| 仮説（あれば） | 「この市場は〜だから自社に機会がある」等の初期仮説 |

### 1-2. 初期仮説の構築

調査を始める前に、チーフが以下の仮説フレームを設定する（調査後に検証する）:

```
仮説1（市場）: この市場は成長しており、受託ニーズが存在するか？
仮説2（競合）: 大手がカバーしきれない隙間（中小企業・日本語対応・カスタマイズ）が存在するか？
仮説3（自社適合）: 業界知識がなくても水平技術力で差別化できるか？
仮説4（収益性）: スタートアップとして持続可能な単価・受注量が見込めるか？
仮説5（タイミング）: 今この市場に参入すべきか？早すぎないか・遅すぎないか？
```

```
- WebSearch と WebFetch を積極的に使い、最新の情報を収集すること
```

```
### A. グローバル市場規模

### C. TAM / SAM / SOM 分析
- TAM（Total Addressable Market）: この技術/サービスの全体市場
- SAM（Serviceable Addressable Market）: 日本市場×受託サービスとして対応可能な範囲
- SOM（Serviceable Obtainable Market）: 創業初期のスタートアップが現実的に狙える範囲

### D. 市場セグメンテーション
- 用途別（モニタリング・デバッグ・コスト最適化・セキュリティ等）
- 顧客企業規模別（エンタープライズ・ミッドマーケット・SMB・スタートアップ）
- 業種別（金融・ヘルスケア・EC・SaaS等）
- 導入ステージ別（PoC・本番導入・運用最適化）

### E. 市場の成長ドライバーと阻害要因
- 成長を加速する要因（規制強化・技術進化・コスト増大等）
- 成長を妨げる要因（技術的課題・予算制約・認知度不足等）

### F. バリューチェーン分析
- この市場のバリューチェーン（誰が何を提供し、価値がどう流れるか）
- バリューチェーン上で受託スタートアップが入り込める位置はどこか

### G. 関連する助成金・補助金
- この領域に適用可能な助成金・補助金制度（IT導入補助金・ものづくり補助金等）
- 受託企業側・顧客企業側それぞれで活用できる制度
```

#### 調査軸5: 顧客インサイト・購買行動分析（市場調査員）

```
[テーマ]の顧客（=買い手企業）のインサイトと購買行動を調査してください。

## 調査項目

### A. 想定顧客のペルソナ設計
以下の3つの顧客セグメントについて、ペルソナを作成:
- セグメント1: 大企業（従業員1000名以上）のAI/データチーム
- セグメント2: ミッドマーケット（100〜999名）のテック企業
- セグメント3: スタートアップ（100名未満）のAIネイティブ企業

各ペルソナに含める項目:
- 意思決定者は誰か（CTO / VP of Engineering / MLチームリーダー / 情シス部長 等）
- 予算権限はどこにあるか
- 現在の課題・痛み（Jobs-to-be-Done フレームワークで整理）
- 導入の動機・トリガー（何がきっかけで検討を始めるか）

### B. Jobs-to-be-Done 分析
顧客がこの領域のソリューションを「雇う」理由を以下のフレームで整理:
- **Functional Job**: 何を達成したいか（例: LLMの品質監視、コスト可視化）
- **Emotional Job**: どんな感情を解消したいか（例: 本番障害の不安、コスト暴走への恐怖）
- **Social Job**: 組織内でどう見られたいか（例: 先進的なチームとして認められたい）

### C. 購買プロセスの構造（日本企業特有の事情を含む）
- 情報収集フェーズ: どこで情報を得るか（カンファレンス・ブログ・ベンダー営業・同業者の口コミ）
- 比較検討フェーズ: 何を基準に比較するか（機能・価格・サポート・日本語対応）
- PoC/トライアルフェーズ: PoCの典型的な期間・規模・評価基準
- 稟議・承認フェーズ: 稟議に必要な材料（ROI試算・セキュリティチェックシート・導入事例）
- 導入・定着フェーズ: 導入後のサポートニーズ

### D. 予算サイクルと購買タイミング
```
